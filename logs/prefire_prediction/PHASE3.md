# 発火前の最善手の値 Phase 3 結果 (2026-10-01)

結論: **事前登録した4構成はすべて門に不合格。本番登録はしない。** フラグ `--prefire-best-play` は既定 OFF のまま。

- 悪化なしの門は、全構成が合格した。
- 改善の門 (発火前3秒 LL ≤ .6958、先読み ≥ 33) は、全構成が届かなかった。
- 主な原因は2つある。
  1. 計算が遅い。1回の計算に P95 で 0.36〜2.2 秒かかる。
  2. 入力 (盤面と NEXT) が毎フレームのように変わる。
  このため、遅れを入れると結果がほとんど表示に出ない。
- 遅れ0 (実時間では不可能) にした診断では、S3 だけの構成で q と発火前3秒が改善した。
  ただし、表示のちらつきが 2.6 倍に増え、zenchi が 18 フレーム悪化した。

事前登録: exev `docs/agent_coordination/DECISIONS.md` 2026-10-01 節 (dc29e73、c8feead)。採点の前に固定した。

## 1. 作ったもの (branch claude/prefire-exchange-prediction-20260930、0438c7b)

- `src/prefire_best_play.py` (状態なし):
  - 既知3手 (手に持つ組 / NEXT / NEXT2) 以内で、各手数の最大発火を求める。
  - 受け側の最善応手の量を求める。
  - E35 で確実な勝ちを証明する。
- `src/prefire_best_play_layer.py`:
  - 二人の選択を合成する。1P は max(p0, 撃つ値)、2P は min(p0, 撃つ値) を取る。
    - 撃たないと窒息する側は、待つを選べない。
    - 両側が改善するなら、手数の小さい側の値を使う。同じ手数なら logit 平均を取る。
    - どちらも待つのが最善なら、値も由来も書き換えない (OFF とビット一致)。
  - 評価器は4構成ある: full / fast / s3 / gfe (§3)。
  - 非同期の遅れ L を模擬する。盤面か NEXT が変わってから L 秒後に結果を出す。その前に入力が変われば捨てる。
- `src/exchange_event_features.py`: `prefire_side_features` に optional の `simulator` を足した。
  - 既定は None で、出力は変わらない。
  - native を使うのは、浮きぷよと UNKNOWN がない盤面だけにした。
  - 記録の盤面 7,500 件で Python 版と一致した (`native_parity/`)。浮きぷよの2件は、振り分けの前は不一致だった。
- replay の CLI に `--prefire-best-play` / `--prefire-best-play-latency` / `--prefire-best-play-evaluator` を足した。すべて既定 OFF。
  - OFF の再生は、本番記録 q と display・events ともバイト一致した (`replay/off_p3/q_7gc4TgFig/DONE.json`)。
- 単体テスト: `tests/test_prefire_best_play.py` 25件。答えが分かる組み立て盤面で確かめた。
  - 今撃つ / NEXT2 まで伸ばして撃つ / 撃てない / 未読 / 不正盤面
  - E35 の証明
  - 合成の規則
  - 受け側が全部返せるなら値が動かない
  - 確実な勝ちで値が跳ぶ
  - 遅れ、撃ち合い中は触らない、構成ごとの評価経路
  - 既存の prefire・replay・production 系 111件も合格した。

## 3. 構成と遅れ (事前登録)

4構成の違いは、撃ったと仮定した撃ち合いの値の求め方だけである。L は、遅れ0の診断再生の P95 を 0.1 秒単位で切り上げた値。

| 構成 | 撃つ値 | 1計算 P50 / P95 (ms) | L |
|---|---|---|---|
| full | logit_mean(S3, 仮想着弾 G_fe) を全発火で求める | 734 / 2,243 | 2.3 s |
| fast | 発火と応手は S3 で選び、選んだ1つだけ合成する | 284 / 637 | 0.7 s |
| s3 | S3 のみ | 193 / 363 | 0.4 s |
| gfe | 仮想着弾 G_fe のみ (待つ値と同じ評価器) | 479 / 1,687 | 1.7 s |

所要は、5記録を最大8本並列で再生したときの値 (loadavg 12〜17)。どの構成も、同期の目安 10 ms を大きく超える。

## 6. なぜ効かなかったか (診断、合否とは別)

1. **入力が毎フレームのように変わる。そのため、遅れを入れると結果がほぼ出ない。**
   - 計算の鍵は、両側の盤面・既知の組・換算率である。
   - 再計算の間隔は、中央値で 1 フレームだった。
   - 鍵が L 秒以上続く割合は、L=0.4 で 5%、0.7 で 2%、1.7 で 1%。
   - 記録の NEXT は、1つの盤面の間にも変わる。q では、盤面の変化 1,732 回に対して、NEXT だけの変化が 4,262 回あった。
     - そのうち未読 (9) を含むフレームが 4,074、A→B→A のちらつきが 199 あった。
     - 1つ先への切り替わり (logs/next_shift/RESULT.md) も含まれる。
   - s3 (L=0.4) で表示が OFF と違ったのは、q の表示 6,526 行のうち 116 行だけだった。
2. **遅れ0なら信号はある。ただし、ちらつきで悪化なしの門を落とす。**
   - これは事後の診断で、門の判定ではない。遅れ0は実時間では不可能で、登録の対象でもない。

   | 構成 (遅れ0) | q LL | 発火前3秒 LL | 先読み | zenchi | 反転 |
   |---|---:|---:|---:|---:|---:|
   | s3 | **.502282** | **.6808** | 38/138 | 7,653 | 887 |
   | fast | .519546 | .6833 | 52/139 | 7,572 | 1,047 |
   | full | .515601 | .6745 | 53/140 | 7,579 | 999 |
   | gfe | .549078 | .7412 | 60/144 | 7,556 | 1,039 |

   - s3 だけが q 全体を改善した (−.0053)。仮想着弾 G_fe を入れる構成は、q を悪化させた。
   - 先読み件数は、対照 (増分を循環ずらし) でも 39 前後になった。
     - 表示が大きく揺れると、偶然でも先読みに数えられる。この指標は揺れに弱い。
     - 発火前3秒 LL の側は、対照で .77〜1.17 と大きく悪化する。こちらは健全だった。
3. 速度の内訳 (s3、q の先頭200秒の profile、1計算あたり)
   - 側特徴 (native、S3 の入力) 約70 ms
   - S3 の評価 約77 ms (うち count 特徴が 53 ms)
   - 3手目の探索 約65 ms
   - MC 応手 約55 ms

## 7. 次の候補 (user 判断・新しい事前登録が要る)

1. **計算の鍵を安定させる。**
   - 盤面と手に持つ組で鍵を作る。NEXT は数フレーム続いた読みだけを使い、未読 (9) では鍵を変えない。
   - 側ごとに分けて計算する。発火の列挙は自分の盤面だけ、応手は受け側の盤面だけに依存する。
   - これで再計算は設置ごと (片側 約1.4回/秒) に減り、遅れがあっても結果が表示に出る見込み (未検証)。
2. **s3 の速度を 100 ms 前後へ下げる。**
   - 3手目の探索を絞る。
   - S3 の count 特徴をキャッシュする。
   - MC の標本数を見直す。
3. **ちらつき対策。** 最善手の値は設置ごとに跳ぶ。ヒステリシスにするか、予測層を別の帯で表示するかは、表示の設計判断 (Codex 担当)。
4. 撃つ値の偏り (撃てば得に見える) の検証。148動画で、撃った撃ち合いと撃たなかった局面の値を比べる。
5. E35 は仮定の撃ち合いでは証明できない。確実な勝ちには、既知ツモを使う証明 (保守性の再検討) が要る。
