## 1. 区切りごとの要約

### 区切り1: 計算の鍵の安定化 (`src/prefire_stable_queue.py`)
- NEXT は、3フレーム続けて同じ実色の読みだけを採用する。未読 (9) と1フレームのちらつきでは、読みも鍵も変えない。
- 手に持つ組 = 1つ前の STABLE 区間の最後の採用読みの next。
- 繰り上がり後かどうかで、既知の組の並べ方を変える:
  - 繰り上がり後: (手に持つ組, next, dnext)
  - 繰り上がり前: (手に持つ組, dnext)
- 繰り上がり後とみなす条件は3つのどれか: 区間内で2つ目の採用読みがある / next が手に持つ組と違う / 採用が区間先頭から0.3秒以上後。
- 入力の正しさ: 5記録のフレーム単位で、実際に置いた組と一致した割合。

  | 並べ方 | 手に持つ組 | NEXT | NEXT2 |
  |---|---:|---:|---:|
  | Phase 4 | 89.4% | 83.4% | 65.3% |
  | Phase 3 | 89.7% | 57.0% | 48.3% |

  - 手に持つ組の規則は、初版の「繰り上がり前なら dnext」(79.2%) より成績が良かったので「常に next」へ変えた。この測定を見て変えたことは、事前登録に書いてある。
- 鍵は片側ごとに作る。探索・応手・死亡証明の結果は、その片側の入力だけで使い回す。
- 鍵の寿命は中央値 0.067 秒のまま、あまり延びなかった。片側の鍵の変化 約1,950回/約15,000フレームのうち、盤面の変化は約870回。
  - 1区間に、読みなし→繰り上がり前→繰り上がり後の3つの鍵があり、両側が交互に置く。
  - そこで非同期の模擬を「届いた最新の結果を使う」に変えた。届くまでに入力が変わっても、届いた結果は使う。撃ち合い中と試合境界では捨てる。

### 区切り2: s3 の高速化 (出力一致のみ、近似なし)
- 3手目の native ビームの幅を1にした。
  - 1手だけの探索では、最大得点は全候補を展開した時点で記録される。幅は、次の深さへ残す数にしか効かない。
  - 最大得点は記録の 6,039 群で全件一致し、所要は 1/7.5 になった。
- 1〜2手目の列挙を、NEXT2 が読める前と後で共有した。fire_lines の出力は Phase 3 版と 360/360 件一致し、所要は 1/3.5 になった。
- 応手 (mc_counter) と E35 を、換算率の鍵でキャッシュした。これらの出力は換算率だけで決まる。
- 1計算の所要 (5記録、5本並列、他エージェント1本と並走)。L の値は事前登録の規則で決めた。

  | | P50 | P95 | L |
  |---|---:|---:|---:|
  | Phase 3 s3 | 193 ms | 363 ms | 0.4 s |
  | Phase 4 | 91 ms | 212 ms | 0.3 s |

  - 採点 run の実測は P50 75 / P95 179 ms だった。
- 残りの約7割は S3 の入力の計算 (近未来火力 near_future_fire_power) である。
  - 内訳: 側特徴 1回あたり約39 ms、count 特徴 約23 ms。
  - P95 を 100 ms にするには、この既存指標を高速化する必要がある。出力一致の検証が要る。

### 区切り3: 値の保持 (`src/prefire_best_play_stable.py`)
- 最善の選択 (採った側と手数) が HOLD_SEC 続いたら表示に出す。HOLD_SEC = 1手の半分 = 0.3665 秒。
- 出すまでの間は、直前に表示していた選択の補正量 (logit の差) を、今の現在値に足す。
- 撃ち合い中 (source != G_fe) と試合境界では、保持を捨てる。発火・着弾・確定死亡は、評価器の値がそのまま即時に出る。
- 補正がなければ、表示も由来も書き換えない。

## 3. 事後の診断 (合否とは別、登録の対象でもない)

- 補正量を λ 倍に縮めて q を採点し直した (trace から計算)。

  | λ | q LL | AUC | 発火前3秒 |
  |---|---:|---:|---:|
  | 1.0 | .51499 | .8004 | .7606 |
  | 0.5 | .50802 | .7949 | .7380 |

  | 0 (=OFF) | .50757 | .7752 | .7308 |

- 発火前3秒の区間は、縮めても改善しない。
  - 順位の情報 (AUC) は、主に発火の直前ではない静止区間で増えている。
  - 発火直前の区間では、最善手の値は撃ち合いの帰結と向きが揃いきらない。
- Phase 3 の s3・遅れ0 (発火前3秒 .6808) との違いは、遅れ・保持・入力の安定化のどれが効いたかを分解していない (未検証)。

## 4. 次の候補 (user/座長判断・新しい事前登録が要る)
1. 補正の較正。最善手の値は順位の情報を持つが、強すぎる。148動画で、現在値と最善手の値の混ぜ方を学習する。
   ただし user 決定 (混合しない) との関係は要確認。λ を5記録で決めるのは過学習になるので不可。
2. 遅れ・保持・入力の安定化を1つずつ外して分解する。どれが発火前3秒を悪化させたかを、148動画か新しい物差しで切り分ける。
