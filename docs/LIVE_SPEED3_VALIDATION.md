`diagnostic_not_quality_pass`。対象は C: の保存入力のみ。配布 d〜h は変更しない。
仮想カメラの g/h は同じ素材だが受理フレーム数が異なり、厳密な対照実験ではない。

## 集計方法

- `diagnose_live_speed3.py`: frame で評価状態・段別計時を結合する。
- 遅延は capture→評価終了。認識完了まで、評価開始待ち、子update/reference、親IPC等の残差へ分ける。
- IPC待ちには子計算が含まれるため、子計算とそのまま足し合わせない。
- CHAIN が片側でもあれば連鎖、残りで OJAMA_FALL があればおじゃま、それ以外はその他とする。
- g の子計時は未保存。探索の内側は g/h とも未保存。欠測を0%と解釈しない。
- 表示pollは `shown != null` のみ。重複pollを含み、フレーム母数の代用にしない。

## 再投入と条件付き実装の判断

- FIX4の保存入力を全件順次再投入し、通知・評価・EMAを省略しない。
- 近未来探索本体と発火候補列挙の実時間を測り、既存キャッシュを通過した呼出の重複を数える。
- 検討基準は探索が更新時間の20%以上、かつ追加LRUの命中候補の実時間が更新時間の10%以上。
- 命中候補時間は最大削減余地であり、改善実測ではない。基準に届かなければ実装を止める。
- 探索キーの診断には盤面、NEXT、色、探索設定、シミュレータ規則、おじゃま換算率を含む。
- 保存入力の重複率と探索本体の重複率を分ける。前者が高くても追加キャッシュ採用の根拠にしない。
- 比較器はFIX4の表示全列のdtype/バイト、events、死亡履歴、証明を照合。探索費用列だけ除外する。
- 重い処理は1本ずつBelowNormal、CPU計算スレッド1。開始前HOLD確認、空き6GiB下限を監視する。

## 候補実装

- `live_near_future_cache` は production_config を単一情報源とする既定OFFのフラグ。launcher→CLI→環境変数→評価子へ配送する。
- 評価子のスコープだけで純関数 `_near_future_search` を外部ラッパーへ置換。認識プロセスや学習・offline既定には適用しない。
- コードSHA256はsrc配下のPythonコードと実際にロードしたnative拡張から生成。キーにはdtype/shape/盤面bytes、NEXT、色、全探索引数、シミュレータ規則、得点換算率を含む。
- おじゃまの状況は上流が作る仮想着弾盤面・残り手数へ反映される。予告に依存する評価結果全体はキャッシュせず、上流処理を毎通知実行する。
- 上限2,048件。先頭32命中は実計算の戻り値をpickleバイトで照合。不一致なら実計算値を返し、以後は再利用を停止。可変戻り値は複製して分離する。
- ON時は子ログの `event_near_future_search` に探索/再利用の処理時間を記録する。`event_update` の内数なので二重に加算しない。
