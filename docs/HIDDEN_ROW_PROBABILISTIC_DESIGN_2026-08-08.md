## 1. 何を変えるのか

**今**: 隠し段 (row 0) が読めないセルは `COLOR_UNKNOWN` (=10) という**単一の値**。
「赤かもしれない」「おじゃまかもしれない」という情報を一切持たない。連鎖シミュレーションは
UNKNOWN を連結対象から除外し (`src/chain.py:238`)、列をそこで分断して落下計算する。
結果、**連鎖数は常に 1 通りしか出ない**。

**これから**: 隠し段セルは**色ごとの確率**を持つ。確率は憶測ではなく、
**すでに分かっている物理・会計情報から**構成する。連鎖数も単一値でなく
**可能性の分布**として持つ。

```
現在   row0: [?] [?] [空] [?] [空] [?]      → 連鎖数 = 5 (1通り)
これから row0: [お100%] [赤50/青50] [空] [お33%/空67%] [空] [赤50/青50]
                                              → 連鎖数 = 5 (52%) / 9 (48%)
```

## 2. 隠し段セルの確率をどう決めるか — 情報源は4つ

優先度の高い順に適用し、**確定した時点でそこで止める** (下位の推測で上書きしない)。

### 情報源A: 重力による確定 (既存・現状のまま)

可視最上段 (row 1) が**空**なら、その列の隠し段も**空で確定**。重力で落ちているはずだから。
現在 `src/image_reader.py:_infer_hidden_rows` がやっていることで、これは正しいので維持する。

> `P(空) = 1.0`

### 情報源B: おじゃま着弾の会計 (user指示の中心)

おじゃまの着弾数はスコア差分から会計できている (`src/ojama_accounting.py`)。
着弾パターンは確定ルール (memory `reference_ojama_landing_pattern`):

> **6列に均等 `floor(N/6)` 個ずつ + 端数 `N mod 6` 個はランダムな列に1個ずつ**

これを隠し段に適用する。ある列の可視部分が埋まっていて、おじゃまが隠し段まで
到達したと会計から分かる場合:

- **均等配分の分 → おじゃま確定**
  例: 14個降った → 各列に 2 個確定。その2個が隠し段に届く列は `P(おじゃま) = 1.0`
- **端数の分 → 確率**
  例: 14個なら端数 2 個が 6 列のどこかに 1 個ずつ → 各列 `P(おじゃま) = 2/6 = 0.33`

> `P(おじゃま) = 1.0` (均等分) / `P(おじゃま) = (N mod 6) / 6` (端数分)

**重要な制約** (memory `reference_ojama_landing_gated_by_placement`):
おじゃまは**連鎖完了後・受け側のツモ着地時**に降る。連鎖中に予告分を先に置いてはいけない。
会計が「予告」段階なら隠し段に反映せず、**着弾が確定してから**適用する。

### 情報源C: 画面外に行ったツモの色 (user指示)

ツモ (2個1組) の色は NextDetector で分かっている (認識精度 100%、
memory `project_next_detector_perfect_accuracy`)。そのツモが積み上がりで隠し段に
入った場合、**そのツモの2色のいずれか**であることが確定している。

- ツモが縦置きで軸ぷよだけ画面外 → その1色で**確定** (`P(その色) = 1.0`)
- どちらが上か判別できない → **2色に等分** (`P(色A) = P(色B) = 0.5`)
- 横置きで2列に分かれる → 各列にそれぞれの色

> 「ツモが行けるところ」に限定するのが肝。**そのツモが物理的に到達し得ない列には
> 確率を置かない**。到達可能列 = 設置操作 (移動・回転) で届く範囲。

### 情報源D: 何も分からない場合

A〜C のどれも当てはまらないセルは、**試合で使われている4色 + おじゃまの一様分布**に落とす。
ただし試合の使用色は和集合で判明している (memory `reference_four_colors_per_match`:
試合は4色のみ使用、1色はランダム除外)。**使われていない色に確率を置かない**だけでも
組み合わせ数が 5 通り → 4 通りに減る。

> `P(各使用色) = 1/(使用色数 + 1)`、`P(おじゃま) = 1/(使用色数 + 1)`

## 3. 連鎖数の可能性分布をどう出すか

### 3-1. 基本の流れ

1. 隠し段の確率分布から**組み合わせを列挙**する (各セルが取りうる色の直積)
2. 各組み合わせについて、確定盤面を作って `simulate_single` で連鎖数を出す
3. 組み合わせの確率 (各セルの確率の積) を、その連鎖数に足し込む
4. 結果 = `{連鎖数: 確率}` の分布

```
{5: 0.52, 9: 0.43, 6: 0.05}   ← 合計 1.0
```

### 3-2. 組み合わせ爆発をどう抑えるか

隠し段は最大 6 セル。各セルが 5 通りなら 5^6 = 15,625 通り。
1 回の simulate が仮に 0.1ms でも 1.5 秒かかり、リアルタイムには乗らない。

抑制策を**この順で**適用する:

| 手法 | 効果 | 備考 |
|---|---|---|
| 情報源A の確定セルを除外 | 大 | 可視最上段が空の列は展開不要。実戦では過半がこれ |
| 使用色4色に限定 | 中 | 5通り→4通り (`4^n` に低減) |
| 確率の低い枝を刈る | 大 | 累積確率が `PRUNE_THRESHOLD` (既定 0.01) を下回る枝は打ち切り |
| 展開セル数の上限 | 保険 | `MAX_EXPAND_CELLS` (既定 4) を超えたら、確率上位のセルのみ展開し、
残りは最頻値で固定。**打ち切ったことを結果に明示する** |

> **打ち切りを黙って行わない**。分布に `truncated: bool` と `covered_probability`
> (展開できた確率の合計) を必ず持たせる。「全部見た」と誤解させないため
> (memory `feedback_stratify_before_pooling` と同じ規律)。

### 3-3. 出力するもの

```python
@dataclass(frozen=True)
class ChainCountDistribution:
    """連鎖数の可能性分布 (隠し段が確定しない場合の表現)。"""
    probabilities: dict[int, float]   # 連鎖数 -> 確率
    truncated: bool                   # 枝刈り/上限で打ち切ったか
    covered_probability: float        # 展開できた確率の合計 (1.0 = 全数)
    n_expanded_cells: int             # 実際に展開したセル数

    @property
    def expected(self) -> float:      # 期待値
    @property
    def most_likely(self) -> int:     # 最頻値
    @property
    def range(self) -> tuple[int, int]:  # (最小, 最大)
```

**単一値が必要な既存コードには `most_likely` を返す** ことで後方互換を保つ
(既存 API のシグネチャは壊さない、CLAUDE.md 規約)。

## 4. どこに入れるか — 既存資産との接続

部品はすでに揃っており、**繋がっていないだけ**である。

| 既存資産 | 役割 | 今回の扱い |
|---|---|---|
| `src/probabilistic_board.py` | 各セルが色確率を持つ盤面 | **器としてそのまま使う** |
| `src/hidden_row_inferrer.py` | 隠し段の確率推論 (W-α) | 情報源D の土台。A〜C を追加する |
| `src/chain.py:simulate_probabilistic` | 確率盤面の連鎖計算 | 分布出力に拡張 |
| `src/ojama_accounting.py` | おじゃま着弾数の会計 | **情報源B の入力** |
| NextDetector | ツモ色 (精度100%) | **情報源C の入力** |
| `src/chain_bitboard.py:simulate_single` | 高速シミュレーション | 各組み合わせの計算に使う |

**新規に書くのは 2 つだけ**:

1. `src/hidden_row_probability.py` — 情報源 A〜D から隠し段の確率分布を構成する
   (stateless な純関数。会計とツモ色は引数で受け取り、認識パイプラインには依存しない)
2. `src/chain_count_distribution.py` — 確率盤面から連鎖数分布を計算する

### 認識パイプラインへの繋ぎ方

`confirmed_board` は単一値の `Board` のままにする (既存の全コードが依存しているため)。
確率情報は**併走する別フィールド**として持つ:

```python
# SideResult に optional で追加 (既定 None = 従来と bit-identical)
hidden_row_probs: HiddenRowProbabilities | None = None
```

これなら既存の指標計算・学習・可視化は一切影響を受けず、必要な箇所だけが
確率を参照できる (CLAUDE.md「optional 引数のみ追加可、削除不可」)。

## 5. 段階的な実装計画

各段階でフラグ既定 OFF、全域バックテストとセット
(memory `feedback_overfitting_awareness_2026-08-04`)。

| 段階 | 内容 | 検証方法 |
|---|---|---|
| **1** | `hidden_row_probability.py` (情報源A+D のみ) + 単体テスト | 既存 UNKNOWN 挙動と一致することを確認 |
| **2** | 情報源B (おじゃま会計) を追加 | 会計値と実画面のおじゃま数を突き合わせ |
| **3** | 情報源C (ツモ色) を追加 | NextDetector 出力との整合、到達可能列の妥当性 |
| **4** | `chain_count_distribution.py` + 枝刈り | 計算時間の実測、打ち切り率の分布 |
| **5** | 発火前予測の測定器に接続 | **下記の検証で効果を判定** |

### 効果の判定方法 — すでに測定器がある

今日作った `scripts/_verify_prefire_vs_actual_chain_2026-08-08.py` が
そのまま検証に使える。発火直前の盤面から予測した連鎖数を、画面表示の実連鎖数と
突き合わせる仕組みである。

現状 (単一値) の実測: **一致 31 / 過小 11 / 過大 1**。
過小 11 件は全て検知経路 `baseline` によるタイミング差だったが、
**隠し段が読めずに連結が切れて過小になっている件がこの中に混じっている可能性**がある。

分布化したあとは、判定基準を次のように変える:

- 単一値のとき: `予測 == 実測` か
- 分布のとき: **`実測が分布の中に含まれるか` + `実測に割り当てられた確率`**

「実測 9 連鎖に対し、分布が {5: 0.52, 9: 0.43} を返した」なら、
単一値なら外れだが分布としては**正しく可能性を捉えている**。この差を測る。

## 6. 設計上の注意点

**確率を憶測で埋めない。** 情報源 A〜C は物理・会計から導かれる根拠のある確率で、
D は「分からない」ことを表す一様分布である。この 2 つを混ぜて「それらしい事前分布」を
作らない。どの情報源で決まった確率かを保持して、後から検証できるようにする。

**連鎖中は適用しない。** おじゃまは連鎖完了後にしか降らない。連鎖中の隠し段に
おじゃま確率を置くと、連鎖中盤面が汚染される (§12.5 の OJAMA_FALL スコープ巻き込みと同族)。

**窒息判定には使わない。** 窒息は 3 列目の可視最上段 (row 1) で判定し、
隠し段 (row 0) は含めない (CLAUDE.md 確定事項、2026-07-22 是正済み)。
隠し段の確率を窒息判定に持ち込まない。

**表示は最頻値ではなく分布を出す。** デモ/オーバーレイで連鎖数を出すとき、
分布が割れているなら「5〜9連鎖」のように**幅で見せる**。単一値に潰して
誤った確信を与えない (自信過剰の較正問題と同じ轍を踏まない)。
