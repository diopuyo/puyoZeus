# 台本素材: このプロジェクトの特徴 (2026-08-09 時点の実測値)

台本の流れは user が作成。 本ファイルは**материал (事実と数値) の提供**が目的。
数値はすべて実測。 推定・目標値には明示的に「目標」と書く。

---

## 1. 一言で言うと

- 対戦動画を入れると「今どちらが有利か」を判定するツール
- **入力は映像だけ**。ゲーム内部のデータやメモリには一切触れていない
- 配信されている画面そのものから盤面を読み取って判断する
- 理屈の上では、どんな配信にも後から乗せられる

## 2. できること (現状)

- 対戦動画 → 盤面の読み取り → 有利不利の判定 → 動画に重ねて出力
- 判定の**根拠 (主因)** も同時に表示する — 何を見てそう判断したかが分かる
- 将棋中継のような評価値グラフを試合全体で描ける
- 認識結果を画面に重ねて、機械が何を見ているかを可視化できる

## 3. 設計思想 (ここが他と違う)

- **形は手段、機能が本質**
  - GTR・階段積みといった形の分類は、あえて一次的な判断材料にしない
  - 測るのは「その盤面が何をできるか」— 火力・厚み・受け・速さ
- **人間が「これが重要」と決めない**
  - 観測できる軸だけを用意し、**どれが実際に勝敗に効くかはデータに決めさせる**
  - 強者の癖や思い込みを持ち込まないため
- **正解ラベルを人が作らない**
  - 「この盤面は有利」の正解は、試合の結末から逆算する
  - 勝敗は画面の勝利数表示から自動で読むので人手ゼロ
- **本命の目的は「人が気づいていない評価軸の発見」**
  - 解説の補助は副次的な用途

## 4. 認識 (盤面を読む) の特徴

- **色の判定に2つの方法を併用**
  - 色そのものを見る方法: 速いが、ぷよの光沢で「空」と誤読する
  - 小さなニューラルネット: 光沢に強いが、学習していないものに弱い
- **「今どういう状況か」を別に判定する仕組みを持つ**
  - 盤面が止まっている / ツモ落下中 / 連鎖中 / 連鎖の段間で落下待ち / おじゃま落下中 / 演出中
  - **盤面が止まっている時だけ読み取り結果を確定する**。動いている間は直前の盤面を凍結
  - 理由: 画面はほとんどの時間なにか動いており、動作中を読むと必ず間違えるため
- 処理速度: 4.42fps → **31fps** まで改善済み (6施策、いずれも盤面差分ゼロを確認)

## 5. 評価 (有利不利を出す) の特徴

- 45個の観測指標を用意し、勝敗データから重要度を学習
- 指標はすべて 0〜1 に正規化
- 学習は 66動画・**73,416ペア**の盤面で実施
- 発火した瞬間に判定へ反映する仕組みを持つ (連鎖終了を待たない)

## 6. 実測値 (数字で言えること)

### 認識
- 盤面認識の精度: **99.54%** (人手で正解を付けた3,744セルとの比較)
- 残り0.46%は**すべて一時的な汚れ**で、1秒以内に自力で戻る。**居座り続ける誤りはゼロ**
- 処理済みの学習データ: **148動画**

### 評価
- 動画ホールドアウトでの勝敗予測 AUC: **0.6615**
- 判定は自信過剰: 「80%有利」と表示した場面の実勝率は **64%**

### 今日 (8/8〜8/9) 見つけて直したもの
- 大連鎖中に判定が逆転する問題 → 解消 (発火の即時反映が無効になっていた)
- 評価が**試合時間の72.3%・最長13.97秒**凍結していた → 片側ずつ更新に変更
  - 直った例: 1Pが撃ち切り2Pが窒息寸前の場面が「互角54%」→ **1P有利97%**
- 非試合画面 (ロビー・順位表・演出) を盤面と誤読 → **全123動画に0.875%混入**を検出、除外の仕組みを実装

## 7. 面白い発見・教訓 (動画向きの話)

### 測り方を間違えると意味がない
- **2つの判定方法が同じ間違いをすると、突き合わせても一致してしまう**
  - 「一致率99%」と出るが、仲良く間違えているだけかもしれない
  - だから人手で正解を作った物差しを別に用意した
- 過去に**測定器そのものが壊れていた事故が5件以上**ある
  - AUCの近似計算バグで「中盤0.630」が幻だった (真値0.516)
  - フレームを間引いて収集すると盤面が壊れる (状態判定への入力が1/6になるため)

### 勝敗を決めているのは何か
- **「今どれだけ大きな連鎖が組めるか」だけでは勝敗はほとんど当たらない**
  - 大連鎖を持っていることと、勝つことは別
- 効いているのは: おじゃまの差 / 連結の数 / 盤面の密度 / 最大連鎖数の差
- **局面によって効く指標が入れ替わる** (今日の実測)
  - おじゃまの差がない局面: 効率系の指標が**すべて無相関** (AUC 0.49〜0.50)、色ぷよの量だけが効く (0.538)
  - おじゃまの差が大きい局面: 効率系が強く効く (0.65〜0.75)
  - 混ぜて集計すると打ち消し合って見えなくなる

### 物理法則を使って認識を検証できる
- 「13段目のぷよは4つ繋がっても消えない」というルールが実装に入っておらず、シミュレーションが誤っていた (今日修正)
- 「おじゃまで7割以上埋まった盤面は実戦なら窒息死が目前で安定継続し得ない」という一点から、非試合画面の誤読を検出できた
- おじゃまの着弾は「6列に均等 + 端数はランダム」という確定ルールがあり、画面外の推定に使える

### AIの限界が出た実例
- **ぷよぷよのルールをAI (私) が取り違えていた**
  - 13段目のぷよが消えないという基本ルールを実装に反映できておらず、user 指摘で初めて是正
  - 既存のシミュレーション実装も同じ誤りを持っていた
- そのため、**ドメイン判断は必ず人間が入る**運用にしている

## 8. 現状の課題 (正直に言えること)

- **材料 (色ぷよの量) の多さを評価できていない**
  - 人間なら「色ぷよが多い方が潜在的に強い」と分かるが、機械が学べていない
  - 既存の指標はすべて「今組める連鎖」を測るので、**材料はあるが形になっていない盤面**を低く評価する
  - 交互作用を追加しても改善は +0.002 (誤差の範囲)。**新しい指標の設計が必要**
- 判定が自信過剰 (80%表示の実勝率64%)。配信に出す前に較正が必要
- 連鎖の終了予測が実際より短く出る (発火時のダメージ見積もりにも影響)

## 9. 今後

- 較正して、表示する数字と実態を合わせる
- 材料の多さを測る新しい指標の設計
- OBSのブラウザソースとしてリアルタイム動作 (最終目標)
- **本命**: データが十分に集まったら「何が実際に勝敗を決めているのか」を改めて調べる

## 11. テストの特徴

- **テスト数 4,349件** (全部パスが常時条件)
- テストコードが本体コードより多い (68,000行 vs 59,000行)
- **1ファイル実装 → テスト通過 → 次のファイル**を原則にしている

### 普通のテストと違う点

- **「変えていないこと」を担保するテストが多い**
  - 改善は必ず「フラグ追加 + 既定OFF」で入れる規約
  - フラグを切れば以前と**1ビットも変わらない**ことをテストで固定する
  - 過去の学習結果・実験結果の再現性を壊さないため
- **引数の並び順までテストしている**
  - 新しい設定は必ず末尾に追加する規約があり、順序が変わると検出される
  - 実際これで、私が入れた変更の順序ミスが機械的に見つかった
- **「採用済みの設定が生成物に反映されているか」をテストする**
  - 改善が既定OFFで入る以上、**付け忘れると機能が存在しないのと同じ**になる
  - 実際に付け忘れて品質が退行した (2026-08-08)
  - そのため採用済み設定を一元管理し、**漏れをテストで機械的に検出する**ようにした (35件)
- **測定器そのものを疑うテスト**
  - 正常なデータでは合格し、壊れたデータでは不合格になることを両方で確認する
  - 測定器が壊れていた事故が5件以上あったため
