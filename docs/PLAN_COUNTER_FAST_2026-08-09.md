## 前提の整理 (実測で確定済み)

### 判定に必要な更新頻度

判定は別に計算して終わり次第反映すればよい。

| 実装 | 実測 | 500ms 予算に対して |

## 見つかった不具合 (2件、 いずれも user 指摘が発端)

### 不具合1: `k_levels` の指定が効いていない
**症状**: K=1 だけを要求しているのに、 K=2 の 256 通りも計算している。
結果、 **K=1 (166ms) が K=4 (69ms) より遅い**という逆転が起きる。

**証拠**:
| 要求 | 実際に評価した件数 | 時間 |
|---|---|---|
| K=1 のみ | `{1: 16}` | **166ms** |
| K=2 のみ | `{2: 256}` | 125ms |
| K=4 のみ | `{4: 24}` | 69ms |
| K=(1,2) 同時 | `{1:16, 2:256}` | **105ms** ← 単独より速い |

「同時に 2 つ頼む方が 1 つだけより速い」は、 **要求に関わらず枝ごと全部計算
している**ことの証明。 プロファイルでも K=1 要求時に
`_counter_reach_exact_k1k2_fast` (K=1,2 をまとめて計算する関数) が呼ばれ、
`_place_pair_to_board` が **5,984 回** 実行されている (16 通りの評価には不要)。

**原因**: 間引きが「exact 枝 / MC 枝」単位でしか効かず、 枝の中の K で
分岐していない。

### 不具合2: 速度差の原因は連結ボーナスではない
user 疑問「差が連結ボーナスだけなのに 3.5 倍の速度差は不自然」→ **その通り**。

プロファイルの内訳 (K=1、 全体 180ms):
| 処理 | 時間 |
|---|---|
| **候補盤面の生成 (純 Python ループ)** | **90ms** |
| ↳ `_place_pair_to_board` 5,984 回 | 83ms |
| ↳ `board.height_of` **15,232 回** | 49ms |
| bitboard シミュレーション本体 | 69ms |

**盤面を作るだけで半分**使っている。 ここは厳密版・近似版で共通。
近似版が速いのは連鎖判定をビット演算で一括処理しているからで、
**連結ボーナスを省いたからではない**。

## 改善案 (優先順)

### 案A: `k_levels` の間引きを正しくする 【最優先・低リスク】
要求された K だけを計算するよう分岐を細かくする。

- 効果見込み: **K=1 が 166ms → 20ms 程度** (16 通りだけ評価すればよい)
- リスク: 低。 既存の結果は変わらない (計算する範囲が減るだけ)
- 検証: 各 K の `n_evaluated` が要求どおりになること + 確率値が現行と一致すること

### 案B: ツモの重複を排除する 【user 提案・効果大】
> 青赤と赤青は本質的に同じ、 などでパターンは減らせる

現状 `_expected_fire_all_pairs` は **4色×4色 = 16 通りを順序ありで**列挙している
(`src/indicators_v2.py:2793`)。 しかし 22 配置の列挙は回転 4 方向を含むため、
**(A,B) と (B,A) は回転で相互に変換でき、 同じ配置集合を生む**。

| | 現状 | 重複排除後 | 削減 |
|---|---|---|---|
| K=1 のツモ | 16 | **10** (同色4 + 異色 C(4,2)=6) | 37.5% |
| K=2 のツモ列 | 256 | **100** | **61%** |
| 生成する盤面 (K=1,2 合計) | 5,984 | **2,420** | **60%** |

さらに **同色ペア (赤赤) は回転 4 方向のうち縦2種・横2種が同一**なので、
22 配置 → 11 配置に半減できる。

- 効果見込み: 盤面生成 90ms → **35ms 程度**
- リスク: 中。 **本当に等価かの検証が必須** (回転の実装に依存する)。
  確率値が現行と一致することをテストで固定する
- 注意: ツモの出現確率としては (A,B) と (B,A) は別事象なので、
  **重みを 2 倍にして数える**必要がある (同色ペアは 1 倍)

### 案C: 連結サイズを bitboard で数える 【精度改善】
現状は連結ボーナスを 0 (=4連結相当) に固定している。 実測誤差:
- 相対誤差 中央値 4.7% / **p90 75.0%** / 平均 21.2%
- おじゃま換算 **p90 14.7 個** (応手判定の閾値 12 個を超える)
- **1連鎖で誤差 29.7% と最大**、 7〜9連鎖では 1.4%
- 実装者自身のテストコメントに「**6連結ケースで exact=600 vs approx=300**」

ライブラリアン調査で、 **bitboard で連結サイズを数える実装は存在しない**ことを
確認済み (3通りの探索)。 新規設計が要る。

方法: グループを 1 つずつ剥がして popcount する
(シードビット → `_expand` で収束 → popcount → 元マスクから引く、 を繰り返す)。
`_POPCOUNT_TABLE_16BIT` と `_expand` は既にあるので流用できる。

- 効果見込み: 精度は厳密に近づく。 **速度への影響は小さい**
  (支配的なのは盤面生成 90ms であり、 連結サイズ計算はビット演算数回)
- リスク: 中。 グループ剥がしの収束回数が盤面依存なので、 最悪ケースの
  計測が要る
- 検証: 厳密版 (`ChainSimulator` + `calculate_chain_score`) と得点が一致すること

### 案D: 盤面生成の Python ループを減らす 【効果大・工数中】
`height_of` が 15,232 回呼ばれている。 列ごとの高さをキャッシュする、
または numpy 化する。

- 効果見込み: 90ms → 30ms 程度
- リスク: 中。 `Board` の内部に触るため影響範囲が広い
- **案A・Bで十分予算内に収まるなら、 後回しでよい**

## 進め方の提案

```
第1段階 (低リスク・即効)   : 案A (k_levels 間引き) → 実測
第2段階 (user提案・効果大) : 案B (ツモ重複排除)   → 等価性テスト + 実測
第3段階 (精度)             : 案C (連結サイズ)     → 厳密版との一致テスト
第4段階 (必要なら)         : 案D (盤面生成の高速化)
```

各段階で:
- **フラグ追加 + 既定 OFF** で入れる (既存の再現性を壊さない)
- **確率値が現行と一致すること**をテストで固定 (案C は意図的に変わるので、
  厳密版との一致で担保)
- 実測して効果を数値で報告

第1・第2段階だけで **166ms → 30ms 程度**が見込め、 1 秒 2 回どころか
**毎フレームでも回せる**水準になる可能性がある。
