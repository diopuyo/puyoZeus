# B3 台帳 v2 (得点ベースの予告おじゃま会計)

作成 2026-10-05。実装 `src/b3_score_ledger.py`、テスト `tests/test_b3_score_ledger.py` (47 件)。
B3 学習行の予告・生成・相殺・着弾・受け量の主入力。旧台帳 (`src/ojama_accounting.py`) は使わない。

## 1. 何を直したか (旧台帳の欠陥)

| 旧 | v2 |
|---|---|
| `_finalize_chain_end` が last_stable_score との差で複数連鎖を 1 塊に記帳 | 掛け算式 (formula_step) ごとに段を対応づけ、連鎖ごとに `ChainRecord` (段・得点・生成・相殺・送出) |
| 予告が連鎖終了後の短時間しか立たない | 得点が入った時点 (式の約 0.9 秒後) で即、受け側の予告に積む |
| 上限 216 で張り付く | 上限なし (テストで 300→400 個を確認)。72 個以上は死亡確定の根拠に使える |
| 落下点・全消しを別計算 | 得点差分に含まれるものとして扱い、端数は繰越 |
| 幻予告 (着弾の条件が無い) | 着弾は「相手の連鎖が終わり、受け側が置き、受け側が連鎖しない」を要求 (§3) |

## 2. 会計規則 (出典)

- 換算 (`ScoreLedgerV2._convert`): 得点増分を `acc` に貯め、連鎖の得点が入った時点で `n = acc // rate`、`acc %= rate`。
  **落下の点も `acc` に入る** (実測: 1P 累計 510 点 = 落下だけの 230 点 + 連鎖 280 点で、2P の予告が 7 個 = 510//70。旧台帳は 4 個)。
- レート: `src.scoring.compute_effective_rate(from_first_move=True)` を再利用 (最初の 1 手から 95.5 秒まで 70、以降 16 秒ごと ×0.75、下限 1、最大 14 回)。
  **起点は両者のうち早い方の最初の 1 手** (`_update_origin`。side 別に持たない)。
- 相殺 (`_offset_own`): 連鎖の各段の n 個は、先に自分の受け予告を古い順に相殺し、余りを相手の予告へ積む。
- 全消し: 連鎖の得点増分が「式の積 + 2100 (+ 落下 26 点以内)」なら全消しボーナスとして帰属し (`cum_all_clear`)、換算にも入る (30 個ぶん)。
- 得点増分の帰属 (`_attribute`): 連鎖段 (式に対応) / 落下 (26 点以下) / 全消し / 未対応の大きな増分 (換算はするが `unmatched_score_jump` フラグ)。式と得点の対応率: video_29 で 1081/1096 段 (98.6%)、得点の遅れは式から 0.87-0.97 秒。

## 3. 着弾 (user 伝授 + 画面照合で具体化)

user 伝授 (reference_ojama_forecast_landing_spec / landing_gated_by_placement) の「相手の連鎖が確定し、受け側の手が置かれ、連鎖が起きなければ降る。連鎖が起きたらその終了後。相殺で消えれば降らない。1 回 30 個まで」に従う。
画面アイコンとの照合で、次の具体化が必要だった (すべて「user 確認要」に挙げる)。

1. 受け側が連鎖を始めた後に確定した予告は、その連鎖の終了では降りない (`_end_chain` は連鎖を始めた手の時刻を基準にする)。
2. 置いた時点で相手が連鎖中 (式が出てから終了前) なら降らない (`_chain_open_at`)。video_29 f31533 で 129 個が降らず 243 個になった実例。
3. 置き終わりの証拠 = 置き終わり信号 / NEXT 移動の立ち上がり / おじゃま落下状態への遷移 (`_lock_evidence`)。置き終わり信号は欠ける手がある。
4. 証拠の時点で相手の連鎖が「終わっていそう」(最後の式から 1.0 秒以上、全段反映済み) なら **仮に降らせ**、待ち時間 (0.6 秒) 内に受け側が連鎖を始める / 相手の連鎖に次の段が来たら取り消す (`landing_revoked`)。画面は置いた直後に減るので、待ってから降らせると 0.6 秒ぶん遅れて不一致になる。

## 4. 連鎖の分割と終わり

- 式の間隔が 2.0 秒を超えたら別の連鎖。式から得点反映までは約 0.9 秒なので、反映後に次の式が来なければ連鎖は終わっている (`formula_gap`)。
- 終了信号 (NEXT 移動 / おじゃま落下 / 静止復帰 3 フレーム) は **最後の式から 1.5 秒以上たってから** 受け付ける。
  段の間 (式の間隔 1.0-1.5 秒) にこれらの信号がちらつき、信号で割ると連鎖が段の間隔 1.4 秒で 87 件 (video_29、全 416 連鎖中) に割れたため。1.5 秒ゲートで 327 連鎖になり過分割は 1 件。
  実際の連鎖終了 (静止復帰) は最後の式から 1.3 秒 (下位 5%)・中央値 1.8 秒・上位 25% で 2.1 秒 (video_29/30)。
- 検出は遅れるので、着弾の前後判定には推定終了時刻 `t_end_est = 最後の式 + 1.0 秒` を使う (検出前でも仮の着弾を許す根拠)。1.0 を 1.3 にしても画面照合の一致は同程度 (合計 85/124 対 88/124) で優劣は付かなかった。

## 5. 因果性と頑健化

- 時刻 t の出力は t 以前の観測だけで決まる (prefix 不変。テスト `test_prefix_invariance`)。
- 得点 OCR: 直近 2 フレームの最小値が採用値を超えたら採用 (1 フレームの読み違い・数値アニメを弾く、採用は 1 フレーム遅れ) + 試合内の単調性 (下がる読みは無視。同じ低い値が 45 フレーム続いたら下げ直して `score_resync_down`)。
  根拠: video_29 で得点が下がるのは試合境界のリセット 52 件だけ (採用値の下がり 52 = リセット 52)。
- 増分の発生時刻 `t_event` (値が最初に現れたフレーム) と、使える時刻 `available_at_sec` を分ける。
- 試合境界: `game_idx` 変化 / 試合外 30 フレーム以上のあとの再開 / 両者 0 点復帰。全状態 (予告・起点・繰越) を捨てる。
- 履歴不完全: 試合の最初の読みが 104 点 (落下 4 手分) を超える動画の途中開始は `history_incomplete` + `margin_origin_unknown` (レート 70 固定)。

## 6. インターフェース (学習行生成器が呼ぶもの)

`src/b3_score_ledger_port.py` が期待する形をそのまま満たす。

```python
from src.b3_score_ledger import ScoreLedger          # 接続口 (dict 入出力)
led = ScoreLedger()                                   # 試合ごとに新しいインスタンス (GameState.reset_game)
snap = led.update(frame_dict, placed_sides=())        # observations の kind=frame の行 / 同フレームの置き終わり側名 ("1P","2P")
# snap = None (試合外・両側スコア未読) か、次のキーを持つ dict
#   available_at, rate, pending_p1/p2, generated_p1/p2, offset_p1/p2, dropped_p1/p2, carry_p1/p2  (契約キー)
#   pending_confirmed_pN, sent_pN, score_pN, chain_open_pN, flags_pN, margin_origin_sec, match_reset, events (追加)
```

- `pending_pN` = 側 N が受ける予告 (相殺後・上限なし)、`generated_pN` = 側 N が生成した累計、`offset_pN` = 側 N が自分の受け予告の相殺に使った累計、
  `dropped_pN` = 側 N へ着弾した累計 (仮の着弾を含む。取り消しで減る)、`carry_pN` = 換算前の端数点、`sent_pN` = 相殺後に相手へ送った累計。
- 型付きで使うなら `ScoreLedgerV2.update(FrameObs) -> LedgerSnapshot` / `replay(frames)` / `iter_record_frames(record_dir)`。
  `events`: `score_attr` (kind=chain/drop/all_clear/unmatched_jump) / `chain_end` / `landing` (provisional) / `landing_revoked` / `match_reset`。
  連鎖ごとの記帳は `ledger.chains` (`ChainRecord`: 段ごとの式・反映時刻・生成・相殺・送出、終了理由、品質フラグ)。
- 置き終わり信号 (events.jsonl の placement_signal) を `placed_sides` で渡すと着弾が良くなる。渡さなくても NEXT 移動とおじゃま落下状態で代替する。

品質フラグ: `history_incomplete` / `margin_origin_unknown` / `unmatched_score_jump` / `unmatched_formula_step` / `score_resync_down` / `chain_without_formula` / `chain_end_by_timeout` / `reset_by_score_zero`。

## 8. 不一致の性質 (目視 + トレースで確認)

1. **着弾の時刻ずれ (最多)**: 台帳が予告ありのまま、画面は直前に降り終わっている。置き終わりの証拠が 0.2-0.4 秒遅れる (NEXT 移動) / 相手の連鎖の終わりが推定より遅い (実際の連鎖終了は最後の式から中央値 1.8 秒)。仮の着弾で大半は縮んだが、1 秒前後の窓は残る。
2. **偽の仮着弾**: 相手の連鎖の最後の段が長く (大連鎖の最終段)、終わっていそうと見て降らせたが実際はまだ降らない。次の段が来なければ取り消せない (video_29 t=2318 で 35 個)。
3. **連鎖終了信号の信頼性**: `next_slide_motion` / おじゃま落下状態が連鎖の段間で出る (式の間隔 2.0 秒以内でまとめた多段連鎖 220 件の 76% に NEXT 移動の立ち上がりが途中で出る。連続した別連鎖を含みうる)。user の絶対律 (NEXT 移動=連鎖終了) を否定するものではないが、記録された信号は段間にも立つ (認識側の信号の精度の問題) → 1.5 秒ゲート。
4. **大きな予告の累積誤差**: 生成の 1 個ずれ・着弾 30 個単位の取りこぼしが 72 個以上の層で効く。
5. **試合境界付近のアーティファクト**: video_29 で試合の切れ目 (MENU 状態と CHAIN 状態が混じる区間、game_idx は前の試合のまま) に両者の得点が同時に +2140 (=2100+40) になる区間が 3 回あり、台帳は相互に 30 個ずつ生成する。原因は未確認。video_30/31 でも同型 (未対応の +2140 前後が両側合計 6-8 件/動画)。
6. 動画の最初 (試合前のデモ画面) にアイコン 35/39 個が表示される (スコア未読の区間)。台帳はスコア未読を試合外として扱うので生成しない。

## 14. 第4版 (2026-10-05): 発生・相殺は得点、着弾は観測 (アイコンは台帳に一切使わない)

方針 (統括経由の user 指示): 発生・相殺は得点から (従来どおり)、着弾は予測せず受け側の確定盤面 (STABLE) のおじゃま (9) の個数の**増分**だけを着弾として予告から古い順に差し引く (予告を超える分は `board_excess` に記録し負にしない)。減る側 (連鎖による消去) は着弾ではなく、0.5 秒続いたら基準だけ下げる。増加は 0.1 秒続いたら着弾 (認識の 1 フレームのぶれ除け)。**アイコンは台帳の値・印に一切使わない** (user: アイコンは大して信頼できない。照合アンカー・下限・着弾補助は実装して撤回、コードから削除)。アイコンは `SideObs.icon_total/icon_count` の参考列として残すだけ。

- 選択: `ScoreLedgerV2(mode="observed")` が第4版 (既定)、`mode="timing"` が第3版 (比較用に残す。第3版でも盤面の観測は診断として走り `board_increase_total` が取れる)。`ScoreLedger` (接続口) のシグネチャは不変、既定は第4版。
- 第4版では置き終わり・連鎖終了の規則は台帳の値を変えない。診断として `landing_predicted` / `timing_ambiguous` の印と、`interrupt` は残す。
- 追加: `observed_landing` イベント (着弾量・盤面増分・列ごとの増分・残り予告)、`board_capacity_limited` 印 (受け側の盤面の空きが 30 個以下で予告が残っている = 着弾が空きで頭打ちになりうる)、snapshot dict に `observed_landing_pN` / `board_increase_pN` / `board_excess_pN`。

- 決着打切り・試合内 MENU を境界にしない・秒単位の定数は第3版のまま。
