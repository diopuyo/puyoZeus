# E22: 窒息条件下のbaseline発火を式・表示得点で確認

基準候補はE19（E15 live count / v3 + 窒息確定後の発火拒否 + 死亡確定表示）。
新フラグ`--death-formula-guard`は既定OFF。
E21の`--death-candidate-guard`とE18〜E20の応手関連フラグは使わない。
`production_config.py`、モデル、特徴量列、対称化・正規化は変更しない。

## 対象と確認規則

- 直前のSTABLE確定盤面（通知内の元発火時刻以下）で`[row=1,col=2]`が既知ぷよに
  占有された側の、新しい`mechanism=baseline`だけを対象にする。隠し段とUNKNOWNは除く。
- それ以外の盤面、formula/formula_read/score_jump/landingの通知は元のオブジェクト・
  発火時刻・triggersをそのまま既存発火処理へ渡す。受理済み連鎖の継続も変えない。
- 元発火時刻以降に有効な掛け算式読取、または発火直前より大きい表示得点を観測すれば
  確定する。式は既存`formula_visible_from_pipeline`が公開する毎フレームの有効読取。
  累積式の保持値・予測得点・会計補正後の得点は確認根拠にしない。
- 発火時刻から通知までの間に観測済みだった式・得点も保持する。発火時刻より前の式を
  別の発火の確認に流用しない。欠測を得点0と扱わない。
- 確認時は保留通知を複製して元の発火時刻のまま返す。認識器のCHAIN状態や通知自体は変更しない。
- 上限内で未確認なら破棄し、経過時間だけで自動承認しない。期限超過後の最初の更新で
  破棄を記録するため、記録上の処理時刻には入力フレームの離散化がある。
  死亡確定・試合境界も破棄する。以後同じbaselineを復活させず、別の式由来通知は通常処理する。

実装: `src/exchange_event_death_formula.py`、接続: `src/exchange_event_overlay.py`。

## 保留上限の事前測定

`scripts/measure_e22_formula_delay_20260928.py`で既存3動画の全baseline通知を走査。
baselineの初通知から同側の有効な式読取までを測り、死亡・試合境界・連鎖終了で打ち切る。
通知直前に読取済みで元発火時刻以降なら遅延0とする。未読取を0として分布へ混ぜない。

全180件中、可測15件、打切り165件。可測例のP99（higher）は0.4666666667秒。
30fps単位に切り上げて**14フレーム、0.4666666667秒**に固定した。
これは可測15件に対するP99であり、打切り例を含む母集団全体のP99とは主張しない。
