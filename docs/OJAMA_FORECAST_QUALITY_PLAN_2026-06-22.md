# お邪魔予告(forecast)品質強化 計画 (2026-06-22)

ユーザー指摘「連鎖中かつ相殺時に予告が更新されない/全体的に予告のみ品質が低い」への強化計画。
**方針=段階的ハイブリッド(ユーザー承認済 2026-06-22)**:明白なバグ修正 + 視覚検出器の精度実測 → データを見て「視覚主軸へ転換するか」を決定。

## 定量調査で判明した真の問題(analyst, video_124_4min 240s/6試合)
| 観点 | 実測 | 判定 |
|---|---|---|
| 連鎖中「凍結」ラグ | CHAIN→STABLE遷移と同時(0.00s)に更新 | **ラグではない**=STABLE時のみ評価する設計挙動。連鎖中に止まって見えるのは仕様 |
| 連鎖終了の破棄(`score_at_chain_start=None`) | 19件中3件=**15.8%**、全て試合境界/大連鎖の山場 | 予告が更新されない直接原因の一つ |
| 極小スコア混入(score差=1) | 79件中28件=**35%** | score OCRが端数を誤読→幻の小お邪魔計上 |
| 試合終了後の残留 | 最終フレームで1Pに122個残留・drainされず | 試合終了時のお邪魔消去処理欠落 |
| `chain_end_triggered`フラグ残留 | 最大30.77s維持(試合境界跨ぎ) | overlay誤表示バグ(forecast値には無影響) |
| 両者同時pending | 0件 | ✅相殺モデルは正常 |
| 予告の出所 | 全件score推定(画面の予告ぷよ表示を読んでいない) | 誤差の構造的根源 |

**結論**: 「連鎖中更新されない」の大半はSTABLE凍結の表示挙動。真の品質低下は「score推定依存」+「境界での破棄/残留」+「端数誤読」。

## 既存資産(眠っている)
- `src/ojama_warning.py` = 予告ぷよ記号を画面から読む `OjamaWarningDetector`(実装済)。ただし①連鎖エフェクト誤読で過去にoverlayから排除 ②記号→個数の`COUNT_TABLE`が通ルール標準と不一致の疑い(月=60/王冠=180 等、アイコン名対応の検証要) ③starテンプレ不在。
- `src/scoring.py` の `OJAMA_ICON_VALUES` は別定義で存在。
- `ojama_warning_glow_guard.py`(発光ガード)流用可。

## 予告ぷよ記号体系(通ルール, Web裏取り)
小=1 / 大(横1列)=6 / 岩=30 / 星=180 / 月=360 / 王冠=720。彗星(1440)は通ルール非登場。表示は最大6アイコン。
※ `ojama_warning.py` の現行 COUNT_TABLE(小1/大6/岩30/月60/王冠180/big_crown360/supercrown720)は名称・値が標準とズレ。**実テンプレ画像と照合して正しい対応を確定してから修正**すること(名称の思い込みで直さない)。

## 強化オプション
- **A 視覚予告 直接認識**: 画面の予告記号を読む。潜在精度最高(正解が画面にある)。要=COUNT_TABLE修正+starテンプレ+CNN再学習+発光ガード。連鎖中誤読はSTABLE限定で回避。
- **B score会計 改良**: 現行維持で境界破棄/端数/残留を修正。低コストだが「画面を読まない」天井は残る。
- **C ハイブリッド(採用)**: STABLE時に視覚予告を読み、score会計値を較正/上書き。視覚失敗フレームはscore会計にフォールバック。既存API破壊せず `calibrate_from_visual(side,count,t_sec)` 追加で実装可。

## 「連鎖中凍結でよいか」への設計回答
有利不利判定はSTABLE時評価が正しく、連鎖中の中間予告値は確定前=雑音。**連鎖終了直後のSTABLEで正しい値が出れば十分**。連鎖中overlayは「推定中」グレー表示にすればUX解決(精度と分離)。

## ロードマップ(段階的ハイブリッド)
### Phase 1(即時・低リスク・視覚主軸判断の前提)
- **1a score会計バグ修正**(`ojama_accounting.py`): 3件の破棄の真因切り分け(試合終了連鎖の破棄は正常/境界誤検知・残留は真バグ)→修正。試合終了時のforecast残留drain。端数誤読(score差=1等)フィルタ。`chain_end_triggered`の試合境界リセット。全て後方互換+テスト。
- **1b 視覚検出器の較正バグ修正+精度実測**(`ojama_warning.py`): 実テンプレと照合しCOUNT_TABLE正値を確定→修正。video_124のSTABLE(非発光)フレームで `OjamaWarningDetector` を走らせ、視覚値 vs 会計forecastの乖離(mean/max・大乖離率・方向バイアス)を実測。→**この数値で視覚主軸への転換是非を判断**。
### Phase 2(1bの結果を見て判断)
- 視覚精度が十分なら: starテンプレ整備+CNN再学習 → `calibrate_from_visual` 実装(STABLE時に視覚値で較正/上書き)→ ハイブリッド完成。
- 不十分なら: B(score会計改良)に留め、視覚はクロスチェックのみ。

## 検証プロトコル
視覚予告認識を正解として会計値との乖離を測定。指標=|visual−forecast|のmean/max、大乖離率(>30個)、方向バイアス。強化前後で全指標30%以上改善なら採用。対象=`forecast>0 & glow=False`のSTABLEフレーム。

## ユーザー判断が要る点(Phase 2入口で再確認)
- 視覚主軸への正式転換(旧方針=score最優先の逆転)は 1b 実測後にデータで合意。
- starテンプレ撮影の工数確保。
- 試合終了連鎖の破棄を「正常」とみなすか。
