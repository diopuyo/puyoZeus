# E17: E16変更の切り分け

## 固定条件

- 基準はE15 live count、`models/exchange_event_v3`。①の同期countだけは対応するv4を用いる。
- 入力は全条件とも`logs/e16/records/`の同一記録。既存3動画、zenchi全編、指定場面のreviewを使用。
- ①は盤面/NEXT同期と初期入力待ち、②は観測死亡後の更新拒否、③は現在層・予測層の分離、等重みlogit合成、信頼性による現在層復帰。
- ③単独でも観測死亡は信頼性理由に含むが、発火・更新は拒否しない。拒否は②だけの作用として切り分ける。
- E16のその他の変更は記録への死亡信号追加、診断出力、モデル版の受入れ、CLI/UIの配線。全条件で同じ入力を使い、①以外のモデルはv3に固定する。
- 採否はq log loss ≤0.5538、zenchi一致率 ≥78.83%、誤発火 ≤1/28だけ。場面改善は追加評価で、未達条件の救済には用いない。
- CVは①のみ。既存E16学習は同期count以外の特徴を変更していないため、保存されたE15/E16の全84,445行・15fold・253,335予測の同一性を検査して再集計する。
- E15/E16基準出力を再用する場合は出典・SHA-256をDONE.jsonへ保存。reviewでは改修後の経路を再生して既存出力とのバイト一致を検査する。
- 新しい独立フラグはすべて既定OFF。`production_config.py`は変更しない。

## ③の照合修正

旧`ExchangeEvaluationLayers._check_completion`は、`chain.side`で選んだ同側の履歴末尾と、発火時の`chain.predicted_final_board`を比較する。
参照: `src/exchange_event_layers.py:117`（側選択）、同`:120`（実行条件）、同`:123`（比較）、
`src/exchange_event_overlay.py:215`（発火時完走予測）、同`:117`（各フレーム末尾で照合）。
`end_signal_sec`が存在し、STABLEで、履歴時刻が終了候補以降なら直ちに照合するため、終了静穏確認を待たない。
終了候補が後で撤回されても`checked`と`mismatches`は取り消されず、次の着手後の盤面も除外しない。
相手側を取り違える添字ではない。一方、おじゃま着弾後の盤面を含め全セル完全一致を要求していた。

指定発火前窓の原因はgame=1・chain=2の1P。終了候補2609.5167秒、次ツモ操作加点2609.8167秒に対し、
旧照合は2610.1167秒の確定盤面を使っていた。次の着手後の盤面で立った不一致が発火前62行まで残存した。
reviewの旧照合15件中14件は`end_confirmed=False`の時点で実行されていた。

③′は`CompletionVerifier`で以下を限定する。
参照: `src/exchange_event_completion_check.py:36`（終了確認・比較）、同`:59`（最初の盤面と着手締切）。

- 同じ側・同じ連鎖の終了候補以後、最初のSTABLE確定盤面を複製して保存し、終了静穏確認後だけ照合する。
- 次ツモ落下・操作加点までに盤面が得られなければ照合しない。後続の新しい盤面で置き換えない。
- 終了候補の撤回・変更で保存盤面と不一致判定を取り消し、新しい終了候補からやり直す。
- おじゃまだけ空白へ置換する。色ぷよを下へ詰めず、座標を含め比較する。UNKNOWNを不一致とは扱わない。

## ①の保持時間

`HOLD_AUDIT.json`と`hold_rows.npz`に全行の採用時刻からの経過秒を保存する。
`different_from_latest`は、時刻が古いだけでなく、元原票の最新STABLE盤面/NEXTと実際に異なる側を対象とする。
その側の最大保持秒数を各行の代表値とし、全84,445行を分母に長期保持率を計算する。
CVの時間帯別値は両側入力取得済みの行に限り、初期入力欠測271行は全体CVから除かない。

最新と異なる入力の保持は74,714行（88.48%）。5秒超46,975行（55.63%）、10秒超22,089行（26.16%）、
30秒超680行（0.81%）、60秒超347行（0.41%）。保持対象の中央値6.633秒、p90=16.134秒、最大1911.267秒。
count特徴は71,750/84,445行で変化。色収支・NEXT繰上がりを再確認するまで前回値を保持する実装に期限はない。
軽量S3のAUCは0.702025→0.685127、log lossは0.623826→0.635148。
10〜30秒帯22,145行のlog loss差は+0.019106だが、1秒未満帯も+0.017372であり、長期保持の長さだけでは全悪化を説明できない。
60秒以上の稀な行では逆に改善しており、極端な長期停止だけを原因とする説明は支持されない。
