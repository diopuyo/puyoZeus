# B3: プロセス分離・C案DTO・DirectShow入力

作業基点: B2検収済み `caabec8`。`production_config.py` と旧本体は変更しない。
評価フラグはB2と同じe14 status.command、`models/exchange_event_v2`。
実行はWSLの指定venv、nice 19、zenchi 2600〜2640秒、warmup 1秒。

## 計装とプロセス境界

- 最初に旧thread経路で計測した。610測定フレーム、認識→評価P95 5,975.276ms、
  FIFO最大30件。warmup込み621通知の評価平均は壁時計46.963ms、スレッドCPU45.387ms。
  最大は壁時計2,229.546ms、CPU2,205.544ms。CPU占有率96.64%で、
  主因は評価計算。壁時計−CPUはGIL/OS待ち等の上限でありGIL単独の実測値ではない。
- `evaluation_profile` は通知ごとの認識完了・評価開始/終了・CPU・バッチ前/内待ちを保持。
  旧threadの固定バッチ待ちは最大0.5秒。`summarize_live_b3_20260928` は
  実バッチ開始と前バッチ終了から待機の重なりを復元する。
  復元した固定待ちのP95は396.117ms、評価の非CPU待ち上限P95は4.834ms。
- B1のFrameMeterを再用し、特徴、M0/G_fe、S1/S3、landingに加え、旧表示補助の
  盤面特徴、MC応手探索 (`counter`)、レビューCSVを排他的に計測する。
  `evaluated_at` は評価値確定時点。後続CSV処理は次の通知の待ち時間に現れる。
  全フレームOFFの評価総時間63.767秒中、MC応手探索44.142秒 (69.2%)、
  旧盤面特徴11.142秒、exchange特徴5.076秒。主な重い処理を特定できた。
- 既定は親監督→spawn評価worker→spawn認識process。CUDA認識器は認識process内で生成。
  `--worker-mode thread` はB2再現用。process経路は固定バッチ起動待ちを外し、通知を到着順に処理する。
  SSEの送出上限2Hzは維持する。
- IPCは確定盤面・状態・得点/式・連鎖イベント・NEXT/スライド・ツモ回数等の変更フィールドのみ。
  生画像、CNN生盤面、推論盤面、確率盤面は送らない。初回に全必要フィールド、以後は差分。
  通知FIFO容量30、満杯なら認識側を待たせる。通知の捨てなし、送受件数を終了時に照合。
  入力映像の古いフレームを捨てる処理とは別である。

## 特徴間引き

`--coalesce-features` は既定OFF。ON時は既に認識された新しい通知がある間、
途中盤面の通常特徴更新・G_fe再計算・旧表示補助特徴/MC探索・レビューCSVを省く。
共有する最新frame番号は計算要否にだけ使い、未来通知の盤面/得点を評価入力へ混ぜない。
EOF/summaryを盤面更新として数えないため、最後の盤面は必ず間引き対象から外れる。

発火、得点、終了信号、落下/着地、確定履歴は全通知で逐次処理する。
発火前の履歴を使う計算、landingの状態処理、交換を閉じるstaticは省かない。
OFFは全フレーム同値を検査。ONは同値を要求せず、同じ全通知列に対する
表示勝率の符号付き/絶対差、評価生値の絶対差、source変更件数をJSONへ保存する。
ONの間引き結果は実行時の滞留状況に依存する。重い単発計算自体は途中で中断しない。

## C案の公開契約

`evaluations.display_layers` を後方互換のoptional欄として追加した。

- `current_p1`: 最後の確定盤面G_fe (`tracker._static_probability`)。未取得はnull。
- `predicted_p1`: 完走/着弾を使う `S3_landing` / `unavoidable_death` の選択評価値。未選択はnull。
- `displayed_p1`: 既存表示平滑化後の実配信勝率。
- `includes_prediction`: 今回の表示入力が上記予測sourceかどうか。既存EMAの過去寄与は別判定しない。
- `prediction_discard_reason`: `unknown_cells` / `observed_exceeds_prediction` /
  `confirmed_board_mismatch` / null。評価器の同名属性があるときだけ転載する。

`contracts.DisplayLayers`、JSON Schema、validator R21で確率の範囲・型・必要値・
破棄と予測込みの排他・実配信勝率との一致を検証する。旧DTOも受理する。
**現評価器は3種類の破棄理由を公開していないので現在はnull。** UNKNOWNや超過等の
部分的証拠から表示側で「予測を捨てた」と推測しない。評価側の理由公開は別タスク。
現在層/予測層の選択ロジックとEMAには手を加えていない。

## DirectShow

Windows上で `--input-config config/live_input.json --duration-sec 40` を指定する。
`config/live_input.example.json` のnameとindexを実機に合わせて設定する。名前検索・自動選択なし。
`--status` はその環境で読めるe14 status.jsonを指定する。デバイス入力の既定実行時間は40秒。

認識processだけが `VideoCapture(index, CAP_DSHOW)` を開く。16:9を確認して1080pへ正規化し、
既存BoardGridDetectorで両盤面枠の位置、ScoreOcrで両得点位置を確認した場合だけ採用する。
未接続・不正比率・内容不一致は勝率なしのHOLD「入力確認中」。採用後も1秒ごとに内容を再確認する。
内部gridが隠れる局面は同じ既存Hough分離器で外枠4辺を照合し、分断線分を重複なく合計する。
zenchi 2600/2605/2610秒の3フレームで内容受理を確認した。
機器別較正の保存先は `config/device_calibration/sha256(name:index).json`。
較正生成/適用と実機確認は次段。偽デバイスで選択・拒否・正規化・解放を検証した。

## 擬似劣化

`scripts/verify_live_degradation_20260928.py` は2599〜2640秒を取り出し、1080p化→
NV12 4:2:0→H.264 yuv420p再圧縮 (CRF23、veryfast、2 threads)。
元入力も既に4:2:0なので、これはOBS/ドライバ固有変換を完全再現する試験ではない。
両側とも同じseed・認識設定・原動画frame番号・時刻で処理し、warmup後の1200フレームを比較した。

両方STABLEかつ確定盤面あり: 725側フレーム、56,550セル中611セル差分。
STABLE成立の相違: 148/2,400側フレーム (元787、変換後811側フレームでSTABLE)。
隠し段を含む13×6セル。これは認識正解率ではなく、同時刻の確定盤面差である。
最初の差は2603.4秒、1P、row3/col4。`logs/live_b3_degradation/boards.npz` と
`comparison.json` に結果・変換コマンド・変換動画hashを保存し、生成動画だけを処理後に削除した。
