# Phase J B11: 長時間保持の解消と検収区間の訂正

基点 `7089978`。同worktree・ブランチで実施。`src/production_config.py` は変更しない。

## 計装で確認した原因

まずB9 longの保存ログを段別に再集計した。5分・5分・残り区間の順に、
認識P95は39.487 / 41.703 / 43.181ms、状態更新P95は0.696 / 0.769 / 0.875ms、
勝率計算P95は194.766 / 237.714 / 275.763ms。
キューput P95は0.041 / 0.041 / 0.043msで、IPC送信待ちが主因ではない。
根拠: `logs/live_b11/b10_diagnosis.json`。

2580.566〜2705秒を非realtime・30Hz全対象フレームで再生し、
認識と評価の別processでtracemalloc・GC型別個数・所有コンテナ長・LRU統計を記録した。
短縮検証では30秒間隔、longでは動画時刻300秒間隔で記録する。
元動画60fpsの30Hz正規化を維持し、負荷による対象フレームの脱落は0件。

- 評価の`ChainSimulator._cache`合計: 0 → 16,390 → 28,401 → 47,350 → 50,060件。
  主な共有キャッシュが50,000件で飽和する。旧実装は満杯になると新しい盤面の
  登録を永久に停止するため、後続試合で繰り返す盤面も再計算になる。
  飽和済みキャッシュに未登録の同一盤面を1,000回与える独立検証で、
  旧方式は1,000回、新方式は1回だけ実計算した。結果盤面は一致。
- 評価のMC登録簿: 2 → 6 → 9 → 15 → 24個。試合境界だけでなく、
  終了信号センサーの生成でも追加され、旧オブジェクト全件を毎通知invalidateしていた。
- 評価の交換記録: 0 → 2 → 3 → 6 → 9件。過去試合のrecords・values・contexts・
  diagnosticsを保持していた。一方、overlayの盤面履歴は1119 → 345件と境界で減り、
  試合を越える単調増加の主因ではなかった。
- 認識監査は1 → 901 → 1801 → 2701 → 3601行と増加。各行に盤面2配列などを保持。
  評価の認識記録・時間計測・FrameMeter、SSEの送出辞書も同様に全件保持していた。
- 認識の未消費ツモは30秒時点で左右3 / 19件、120秒時点で25 / 83件。
  `force_in_match`の経路では古い試合の未消費分も残る。消すと以後の累積制約の
  入力が変わるため、値を捨てずディスクFIFOへ移した。
- 認識の直近得点は各30件、背景指紋の形キャッシュは144件で安定。
  入力画像は前回1枚（6,220,800 bytes）。小さいLRUの上限は既存どおり。

根拠: `logs/live_b11/baseline_memory/{recognition,evaluation}.jsonl`。
初回計装では全projectオブジェクトへのvars()がPythonの遅延__dict__を生成したため、
後の計装はコンテナ所有型に限定した。初回のtracemalloc/RSS絶対量と修正後の量を
そのまま改善率に使わない。上の保持件数・キャッシュ飽和実験はこの影響と区別する。
tracemalloc有効時の実行時間は配信性能の合格判定に使わない。

## 修正

- ライブprocess内だけ、連鎖キャッシュを1インスタンス最大2048件のLRUへ交換。
  既存singletonと新規生成の両方へ適用し、offlineの既定キャッシュは維持する。
- MC登録簿を弱参照化。executor所有者は終了処理のため保持する。
  通知ごとのinvalidateは実際に使用中の2トラッカーだけに限定する。
- 試合境界で交換記録と診断をディスクへ退避し、records・contexts・診断重複キーを
  破棄する。交換IDは単調採番を保ち、終了時には全試合の記録を再出力する。
- 認識監査・評価計測・タイムライン・SSE・捨て時刻をディスクへ逐次退避する。
  append後に補足される計測列を失わないよう、RAMには直前1行だけ残す。
- 認識が現在frameの出力へコピー済みの診断を退避し、過去alertの毎frame全走査を除く。
  未消費ツモは順序と件数を維持するディスクFIFOとし、認識上のリセットは追加しない。
- 入力記録器の静止特徴キーの重複除去setは試合境界でクリアする。
  再記録が増えるだけで、特徴計算と評価値には影響しない。

`PUYO_BOUNDED_HISTORY=0`で旧保持経路、`1`（ライブ既定）で修正経路を選択できる。
offline CLIはこのライブadapterを通さない。元の評価関数・認識設定は変えない。
監査の一括JSON/NPZ生成は運転終了後に行うため、その時点の一時メモリは定常運転と区別する。
