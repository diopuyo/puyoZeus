## 1. 直す対象

`FormulaStepAccumulator.update()` (`src/score_ocr.py:1039-1089`) の段同一性判定。

### 現行の 2 つの欠陥

| # | 場所 | 内容 |
|---|---|---|
| 1 | `:1065-1070` | 直前確定段と (左辺, 右辺) が完全一致する読取りを、**経過時間を問わず**「同じ段の再読」として棄却する |
| 2 | `:1072-1076` | 右辺が減少 or 同値なら、消失ギャップ ≥ `FORMULA_NEW_SESSION_MIN_GAP_SEC` (0.5秒) で **セッション破棄 (全段消去)**、未満で **段の棄却** |

### 前提が物理的に誤っている

現行 docstring は「右辺 (ボーナス倍率) は同一連鎖内で単調増加する」と書くが、
`src/scoring.py` のボーナステーブルに照らして誤り。

```
段の素点 = (消したぷよ数) × 10 × max(1, 連鎖ボーナス + 連結ボーナス + 色数ボーナス)
                                      ^^^^^^^^^^  ^^^^^^^^^^^^  ^^^^^^^^^^^^
                                      単調増加     段ごとに変動   段ごとに変動
```

- 連鎖ボーナス `[0, 8, 16, 32, 64, 96, ...]` — 1→2 段の増分は **+8** しかない
- 連結ボーナス (4個→0, 5→2, …, 11個以上→10、グループごとの和) と
  色数ボーナス (1色→0, 2色→3, 3色→6, 4色→12) の合計は **最大 22 程度**まで動く

したがって右辺は同一連鎖内で**減少も同値もし得る**。

### 実測した壊れ方 (同じ現象が幕間 0.1 秒の揺らぎで真逆になる)

1 連鎖目 = 11個の1色連結 (左辺110・右辺10)、2 連鎖目 = 4個消し1色 (左辺40・右辺8)。
右辺は 10 → 8 と減るが、これは正当な同一連鎖の 2 段である。

| 幕間 | 修正前の動作 | 残る段 | total_power |
|---|---|---|---|
| 13f (0.433秒) | 2 段目を**棄却** | (110, 10) | **1,100** |
| 15f (0.500秒) | **セッション破棄** | (40, 8) | **320** |
| 16f (0.533秒) | **セッション破棄** | (40, 8) | **320** |
| 19f (0.633秒) | **セッション破棄** | (40, 8) | **320** |

正しい答えは **2 段・1,420**。段数はどちらも 1 だが**残る中身が真逆**で、
火力が 3.4 倍ずれる。

## 2. 段の区切りの正しい信号 = 「幕間」

### 2.1 コードのコメントが測定結果を誤引用していた

`src/score_ocr.py:111-115` は

> 同一連鎖中は掛け算式が連続表示される (402 フレーム実測) ため、
> 表示が途切れずに右辺が減る読取りはフェードアウト/遷移中の部分読みであり棄却する

と書くが、**402 フレームの実測はレイアウト不変性の測定**である。
`reference_chain_formula_layout_2026-08-24.md:41`:

> | 段が進んだとき | **位置・サイズ不変** (10ケース×402フレームで y=30±1、倍率1.0のみ) |

**時間的連続性は測っていない。**

### 2.2 実際は掛け算式と通常スコアが排他で、段間に必ず幕間が入る

`src/recognition_pipeline.py:6272-6273`:

```python
if cached_score_val is not None:
    return None  # 通常スコア表示中 (掛け算式と排他)
```

実測 (`logs/_diag_formula_fix_e2e_2026-08-24/trace_on.jsonl`、1P の 15 連鎖・13 境界):

| 項目 | 実測 |
|---|---|
| 1 段の表示 | 各 **28 フレーム (0.933 秒)** で一定 |
| 段間の幕間 (通常スコア表示) | **13〜19 フレーム (0.433〜0.634 秒)** |
| 幕間中のスコア増分 | **直前段の「左×右」と完全一致 (12/12)** |

実画面でも確認済み:

- `logs/_diag_formula_fix_e2e_2026-08-24/screen_1p_t6697.6.jpg` — スコア欄に「40× 1」

**`FORMULA_NEW_SESSION_MIN_GAP_SEC = 0.5秒` は幕間分布 0.433〜0.634 秒の
ど真ん中に刺さっている。** どちらに転んでも壊れる理由がこれ。

## 3. 【最重要】配線ギャップ — 累積器は幕間を観測できない

**修正は累積器のロジックだけでは完結しない。**

`src/recognition_pipeline.py:4860, 4864`:

```python
if self._formula_accum_1p is not None and self._formula_last_read_1p is not None:
    self._formula_new_step_1p = self._formula_accum_1p.update(
        time_sec, self._formula_last_read_1p,
    )
```

`_read_formula_value` は通常スコア表示中に **None を返す**。
したがって**幕間のフレームでは `update()` が一度も呼ばれない**。
累積器は幕間を原理的に観測できない。

配線を直さない限り、累積器側をどう作り替えても効かない。
これは配線事故が 8 件記録されているプロジェクトなので
(`feedback_wiring_gap_vs_wiring_error_2026-08-22`)、
**非汎用スクリプトによる配線確認を検収条件にする**
(`feedback_wiring_check_needs_nongeneric_scripts_2026-08-18`)。

### 3.1 「幕間」と「読取り失敗」を混同してはいけない

`_read_formula_value` が None を返す理由は 2 通りある。

| 理由 | 意味 | 段の区切りとして使ってよいか |
|---|---|---|
| `cached_score_val is not None` | **通常スコアが読めた** = 掛け算式は表示されていない = 幕間 | **使ってよい** |
| `self._score_ocr is None` / 例外 | 読み取れなかっただけ。掛け算式が出ているかは不明 | **使ってはいけない** |

後者を幕間と誤認すると、**存在しない段を積む** (過大方向の事故)。
よって渡す信号は「読取り失敗」ではなく
**「通常スコアが読めた」という肯定的な観測**にする。

> これは Q-08 (「重要な OCR 失敗が無記録で握りつぶされる」) と同根である。
> 現状 `_read_formula_value` は全例外を None に潰し、原因も回数も残さない。

## 4. 修正の設計

### 4.1 API (backwards compat: optional 引数の追加のみ)

```python
class FormulaStepAccumulator:
    def update(
        self,
        t_sec: float,
        result: "FormulaReadResult",
        *,
        score_displayed: bool = False,   # ← 追加。既定 False で従来挙動
    ) -> "FormulaStep | None":
        """読取り 1 件を反映する。

        Args:
            score_displayed: このフレームで**通常スコアが読めた**か。
                True は「掛け算式が表示されていない」ことの肯定的な観測であり、
                段の区切り (幕間) を意味する。読取り失敗では True にしない。
        """
```

呼び出し側 (`recognition_pipeline`) は、掛け算式が読めなかったフレームでも
`score_displayed=True` を添えて `update()` を呼ぶ。

### 4.2 判定規則

```
幕間フラグ = 直前に段が確定して以降、score_displayed=True が
             confirm_frames 連続したフレームが 1 度以上あった

新しい段として受理する条件:
    幕間フラグが立っている、または 値が直前確定段と異なりかつ旧規則を通る
  かつ
    同一値が confirm_frames 連続した
```

- 幕間フラグが立っていれば、**値が同一でも / 右辺が減っていても**受理する。
- 幕間フラグが無いときは**旧規則にフォールバック**する
  (フェード中の部分読みはここで棄却される)。
- 段を確定したら幕間フラグを落とす。次の段には次の幕間が要る。

#### 4.2.1 幕間にも連続確認を要求する (過大方向の事故の防止)

**幕間フラグを 1 フレームで立ててはいけない。**
通常スコアの単発誤読で立つと、直後のフェード部分読み
(「50×386」→「50× 86」) を新しい段として拾ってしまう。
これは**存在しない火力を作る**方向の事故で、段を取り逃す (過小) より危険である。

そこで幕間にも段確定と同じ `confirm_frames` の連続を要求する。
実測の幕間は 13〜19 フレームなので、**本物の幕間を取り逃すことはない**
(13 ≫ 2)。掛け算式が読めたフレームで連続カウンタはリセットする。

### 4.3 定数

| 定数 | 扱い | 根拠 |
|---|---|---|
| `FORMULA_NEW_SESSION_MIN_GAP_SEC` (0.5秒) | **幕間フォールバック時のみ維持** (下記の実装後訂正を参照) | 幕間が観測できる経路では使わない |
| `FORMULA_SESSION_RESET_SEC` (2.0秒) | **維持** (フェイルセーフへ格下げ) | 実測の段周期 max 1.700 秒 (10ケース288間隔) < 2.0 |
| `FORMULA_STEP_CONFIRM_FRAMES` | **2 のまま据え置き** (下記の実装後訂正を参照) | — |
| 新規の時間定数 | **不要** | 区切りがイベント駆動になるため |

**シーンからの逆算は一切していない** (`feedback_overfitting_awareness_2026-08-04`)。

#### 【実装後の訂正 2026-08-24】設計から 2 点変えた

**① `FORMULA_NEW_SESSION_MIN_GAP_SEC` を廃止せず、フォールバックとして残した。**

当初は「廃止」としていたが、実装時に**幕間を観測できない場合の受け皿が要る**ことが
分かった。掛け算式も通常スコアも読めない区間 (バースト、煙、フラグ OFF) では
幕間フラグが立たないので、その場合は従来規則に落とす。

副次的な利点として、**既存テストを 1 つも書き換えずに済んだ**。
`tests/test_formula_value_read.py` の 32 件は幕間を渡さない呼出しなので、
そのまま旧経路を通って全て緑のまま。§5 では「書き換える」としていたが**不要だった**。

**② `FORMULA_STEP_CONFIRM_FRAMES` は 2 のまま据え置いた。**

3 への引き上げは reviewer の推奨だったが、根拠の「部分読みの持続は最大 2 フレーム」
自体が**裏取り不能**と明記されていた。一方で 3 にすると既存テスト
`test_accumulator_confirms_after_two_frames` を書き換える必要が生じる。

幕間規則の導入によりフェード部分読みは「幕間が無い」ことで既に弾けるので、
**証拠の弱い変更で既存テストを壊す理由がない**と判断した。
必要なら別途、部分読み持続の実測を取ってから決める。

### 4.4 検算 (採用しないが、カウンタには出す)

幕間中のスコア増分は直前段の「左×右」と一致するはず (実測 12/12)。
一致しない件数をカウンタに出す。
**一致しないことを理由に段を棄却はしない** — 過小 (段を取り逃す、検知可能) の方が
過大 (偽の段を積む、検知困難) より安全なので、
幕間が観測できたなら受理し、検算の不一致はログに残すだけにする。

物理制約「段の素点 = 左辺 × 右辺、左辺は 10 の倍数」
(`docs/KNOWN_WEAKNESSES.md` W2) も同様にカウンタで見る。

## 6. chain_id との階層関係

`FormulaStepAccumulator` は **段の確定器に徹し、セッション境界の自己判断をやめる**。

- **内側 (accumulator)**: 掛け算式を読んで段を確定し、`(t_sec, left, right)` を出す。
- **外側 (chain_id 付与器)**: 段 + 連鎖終了の絶対律信号を受けて `chain_id` を管理する。
  **chain_id が閉じたら、pipeline が accumulator のセッションを明示リセットする。**

連鎖の始まり / 終わりは盤面信号 (連鎖側のネクストが動く / おじゃまが落ちる) を
見られる側にしか正しく判定できない。値のヒューリスティクス (右辺減少) で
連鎖境界を推定するのは構造的に不可能である
(新連鎖 1 段目の右辺と、同一連鎖内の揺らぎは値域が重なる)。

**実装ギャップ**: 現状の accumulator リセットは試合切替のみ
(`src/recognition_pipeline.py:3958-3965, 4457-4460`)。
**連鎖終端でのリセット配線は存在しない。**

タイムアウト 2.0 秒と `CHAIN_ID_MAX_SEC` はフェイルセーフとして残し、
発火したら必ずカウンタに出す。

詳細は `docs/EXCHANGE_EPISODE_SPEC_2026-08-24.md` §5.2.3。
