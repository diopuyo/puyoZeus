# E34: 予測用起点の保存ガード

## 状態

**入力不足によりON検収未成立。性能不合格とは区別する。**
比較基準はE32（b7fa3e9）の `--prefire-snapshot --hidden-row-belief`。
E33/E33bの候補除外は使用せず、E33bで固定した得点誤差の母集団だけを引き継ぐ。
`production_config.py` は変更しない。

## 実装

既定OFFの `--prefire-origin-guard` を描画・保存入力再生に追加した。
描画側で収集側の `enable_landing_chain_record_hold` と
`enable_chain_active_record_hold` を有効にし、既存の `landing_chain_started` を
予測用入力 `prefire_origin_hold` として保存する。保持期限の再推定や新しい判定器は作らない。
試合範囲は収集側と同じ `src.match_range_gate.build` と `MatchRangeGate.allows` を使う。

予測専用履歴はSTABLE・確定盤面あり・試合範囲内・連鎖保持中でない行だけで更新する。
予測を開始するときに通知を複製し、`before_board` を発火時刻より前の最後の適格盤面にする。
これにより連鎖途中の通知が持つ盤面で起点を上書きしない。
元の通知、現在層の `_history`、確定盤面、STABLE判定、隠し段の学習履歴は変更しない。
試合境界では予測用履歴も消去する。

起点ガードONで試合範囲が無い場合や保持印が未取得の場合は明示的に停止する。
収集側の「範囲ファイル不在なら未適用」という状態をE34適用済みとして採点しないためであり、
ゲーム状態の新たな判定ではない。OFFでは新フィールドも新ゲートも参照しない。

## ONを測れなかった根拠

1. E32の固定入力である `logs/e31/records` の全5入力にW48b保持印がない。
2. 保存ヘッダーの動画IDに対応する `match_boundaries_v4/v5/<video_id>/matches.tsv` が
   worktreeにない。共有元の同ディレクトリ・動画索引でも対象IDとの対応は確認できなかった。
3. 元動画を同じ認識設定で再生して保持印だけを補完する試みは、qの1.800秒・1Pの
   `confirmed_board` が元記録と不一致になった。直前54フレームまでは全保存認識項目が一致。
   元と同じ乱数シード、および元のE8描画コマンド全体を使う3秒検査でも同じ位置で不一致。
   原因そのものは未特定。不一致の認識履歴の保持印をE32入力へ転用していない。

生入力は保存済みE32のまま保持した。未完成の補完ファイルは `.tmp` とし、
正式なON入力 `.jsonl.gz` として公開していない。
再開には対象動画の既存試合範囲と、元認識と一致する保持印の記録・復元が必要。
