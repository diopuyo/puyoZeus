# 既知の問題と対策案 — 2026-04-26

ぷよぷよ分析プロジェクトで現時点 (Phase 3 e2e 検証完了時点) に未解決のままになっている問題を整理し、短期 / 中期 / 長期の対策候補を提示する。

## 1. CNN holdout 精度 0.9266 で頭打ち（訓練データ不足）

### 状況
- `data/global_best.json` の holdout 精度は 0.9266 (Cycle 5 達成、Cycle 6 で更新なし)
- 内部精度は 0.9911 で内部・holdout のギャップ ≈ 6.4 pt → 過学習傾向
- 直近 6 サイクル累計 +9.68pt 改善後、改善が逓減

### 推定原因
1. パッチクラスの分布偏り: video_01/02 中心、video_03 由来パッチがマイノリティ
2. 暗所紫が `空` と誤認されやすい (背景色との類似)、5-10× 拡張済みでもまだ少数
3. ぷよぷよの色配置が「実盤面で出現するパターン」しか得られない (合成データなし)

### 対策候補
| タームスケール | 対策 | 期待効果 |
|---|---|---|
| **短期** | B-1 統合: `extract_from_frame_with_sides` + `balance_dataset(stratify_by_side=True)` を `long_improve_v2.py` に組込み | 1P/2P バランス偏り解消で holdout +0.5〜1.0pt |
| **短期** | `data/training/parallel/` のラベルノイズ手動レビュー (暗所紫だが実は空のパッチ) | ノイズ除去で +0.2〜0.5pt |
| **中期** | 合成データ生成 (盤面状態 + 既知の色テンプレ → 合成パッチ) | 暗所紫マイノリティクラス強化 |
| **中期** | アノテーションツール `scripts/collect_human_labels.py` 拡張、video_03 中心に 500 パッチ追加 | データ多様性向上 |
| **長期** | より大きな CNN (ResNet18 ベース) + GPU 利用率向上 | パラメタ容量増で +1〜2pt |

## 2. 動画勝敗予測 holdout 精度 0.519 で頭打ち（プレイヤー戦術差）

### 状況
- 勝敗予測 (LogisticRegression) の動画 holdout test_acc=0.519、ベースラインとほぼ同等
- フェーズ別: midpoint 0.548, end_minus_5 0.548, start_plus_20 0.571 (最高)
- `LEARNED_WEIGHTS_END` などは「敗者の方が指標が高い」など符号が反転

### 推定原因
1. **プレイヤー個性**: 同じ「本線完成度 0.6」でも、攻撃型は仕掛けて勝つ、守備型は耐えて勝つ → 16 指標だけでは対応できない
2. **試合フェーズの曖昧さ**: 序盤・中盤・終盤を時刻基準で固定したが、試合長は 31〜119s と幅がある
3. **3 動画 (715 サンプル)** はロジスティック回帰には十分でも、戦術多様性をカバーするには小さい

### 対策候補
| タームスケール | 対策 | 期待効果 |
|---|---|---|
| **短期** | フェーズを時刻ではなく相対進捗 (試合長に対する 0.0〜1.0) で定義 | midpoint 精度 +1〜2pt |
| **短期** | プレイヤー ID をワンホットで特徴量化 (戦術差を吸収) | holdout +2〜3pt |
| **中期** | 試合数 715 → 5,000 へ拡大 (新動画 7 本追加 DL) | 統計安定で +3〜5pt |
| **中期** | 時系列 LSTM/Transformer で試合シーケンスを直接モデル化 | フェーズ依存性吸収 |
| **長期** | 自己対戦シミュレータで擬似データ生成 (モンテカルロロールアウト) | 戦術空間を網羅 |

## 3. 高度指標の評価重みが counter-intuitive（符号反転）

### 状況
- `LEARNED_WEIGHTS_GLOBAL` で `INDICATOR_TOUCHING_DENSITY = -2.7013` (本来は連結が多いほど有利のはず)
- `INDICATOR_OFFSET = -0.3474` (相殺力は本来正)
- `LEARNED_WEIGHTS_END` ではほぼ全指標が負

### 推定原因
1. **多重共線性**: `main_chain_maturity` と `touching_density` は強い正相関 → ロジスティック回帰が片方に係数を集中、もう片方を相殺方向に置く
2. **終盤バイアス**: 試合終了 5 秒前は「敗者が苦し紛れに大連鎖を組もうとしてフィールドが崩壊」する → 形評価が高くても負ける
3. **`offset_power` 飽和**: ojama_equiv が MAX_OJAMA_OFFSET=72 で頭打ちし、勝敗との相関が弱まる

### 対策候補
| タームスケール | 対策 | 期待効果 |
|---|---|---|
| **短期** | `MAX_OJAMA_OFFSET` を 72 → 144 に引き上げて再学習 (offset_power 飽和解消) | offset 重み正常化 |
| **短期** | L1 正則化を強化 (C=5.0 → C=1.0) して係数スパース化 | 多重共線性低減 |
| **中期** | 指標相関行列を可視化し、相関 0.8 以上のペアは片方を削除 | 解釈可能性向上 |
| **中期** | DEFAULT_WEIGHTS を継続採用 (現状)、LEARNED_WEIGHTS_* は実験的扱い | 直感的な可視化を維持 |
| **長期** | 因果推論 (DoWhy) で各指標の真の因果効果を測定 | 戦術根拠の科学化 |

## 4. ネクスト枠 ROI が UI レイアウト依存（再キャリブ必要）

### 状況
- 1P 用 ROI は v10 で確定、2P 用は中央 x=960 で水平ミラー
- すべての座標がぷよぷよチャンピオンズ標準 1920×1080 UI 前提
- 別大会・別解像度・別画面構成 (例: ぷよぷよeスポーツ Steam UI) では再キャリブ必須

### 推定原因
- ROI を直接ハードコード (`src/next_detector.py`) しているため移植不可

### 対策候補
| タームスケール | 対策 | 期待効果 |
|---|---|---|
| **短期** | ROI を `src/calibration.py` に統合し、`models/calibration.json` で外部化 | 別 UI でも JSON 差し替えで対応可 |
| **短期** | `python -m src.cli calibrate` のフローにネクスト ROI も含める | 大会別 calibration 1 ファイル作成で完結 |
| **中期** | 画面 OCR で「NEXT」テキスト位置を自動検出してネクスト枠を推定 | 完全自動化 |
| **長期** | 物体検出モデル (YOLOv8) で盤面・ネクスト枠を End-to-End 検出 | 任意 UI 対応 |

## 5. WIN OCR 未実装（現状画像差分のみ）

### 状況
- `src/match_winner.py` は数値画像差分 (16×16 二値ハッシュ + Hamming 距離) で勝敗判定
- video_02 で 50/50 全試合判定成功だが、別動画では精度未検証
- `src/win_panel.py` は ★WIN★ パネル位置のみ検出、勝数 (例 "1-0" / "2-1") は読まない

### 推定原因
- OCR (Tesseract / EasyOCR / PaddleOCR) を導入していないため
- 数字認識用の `data/verify/digit_samples/` は収集済みだが分類器未訓練

### 対策候補
| タームスケール | 対策 | 期待効果 |
|---|---|---|
| **短期** | `digit_samples/` を 10 クラス CNN で訓練し WIN 数値読取り | 試合スコア把握 |
| **中期** | EasyOCR を導入し WIN ラベル + 残り時間を一括 OCR | 試合状況の完全把握 |
| **長期** | リアルタイム配信での試合進行 (試合数・スコア) を OBS 経由で表示 | 観戦体験向上 |
