# ぷよ認識のしくみ — 詳細資料 (2026-08-05版・実装準拠)

専門用語を使わずに、対戦動画から盤面を読み取る「目」の仕組みを深いところまで説明する資料。姉妹資料: 全体まとめ (PROJECT_SUMMARY_PLAIN_2026-08-04.md) / 指標と頭脳 (INDICATORS_AND_BRAIN_PLAIN_2026-08-04.md)。技術的な正式名はカッコ書きで添える。

---

# 1. 何を読み取っているか

入力は対戦動画 (1920×1080、毎秒30または60コマ)。画面には2人分の盤面が映っており、それぞれについて毎コマ次を読み取る:

- **盤面**: 6列×13段のマス目。各マスは「空 / 赤 / 青 / 緑 / 黄 / 紫 / おじゃま」のどれか。最上段 (13段目) は画面にほぼ映らない「隠し段」
- **スコアの数字** (数字読み取り = OCR)
- **次に来るぷよ2組** (ネクスト・ネクネク)
- **試合の状態**: 試合中か、試合と試合の間の演出中か
- **勝敗**: 試合終了時の勝ち数表示 (差分が増えた側が勝者)

出力は「確定盤面」— 信頼できると判断した瞬間の盤面のスナップショット列で、これが指標計算・学習・勝率表示すべての土台になる。

# 2. 色の読み取り — 二重チェック + 動画ごとの自動チューニング

## 2-1. 2系統の判別器

各マスの色は独立した2系統で読み、突き合わせる:

1. **色味方式** (HSV): マスの画素の「色相・鮮やかさ・明るさ」の統計から色を決める。速くて素直だが、照明や演出に弱い
2. **ニューラルネット方式** (CNN): マスの画像そのものを学習済みネットに見せて判別。柄や質感まで見るが、見たことのない見た目に弱い

2系統が一致したマスは信頼度が高い。食い違ったマスは慎重に扱う (すぐには採用しない)。

## 2-2. 動画ごとの色味の違いへの自動対応 (オンライン較正)

動画によって画質・圧縮・明るさが違うため、**再生しながらその動画専用の「色の物差し」を自動で作る**:

- 静止確定した盤面の中から信頼できるマスの色サンプルを貯める (連鎖中は演出で色が変わるため収集しない)
- 十分貯まったら、色味方式の基準範囲をその動画向けに1回だけ上書きする

以前は動画ごとに人手で調整していたが**廃止済み**。「自動較正のみで99.5%以上」を汎用化目標に据えて達成している (実績99.7%)。動画を100本に増やしても人手作業が増えないのはこの仕組みのおかげ。

既知の限界: ①サンプルが貯まるまでの立ち上がり時間帯は素の基準で走る ②これは「動画の恒常的な色味」への適応であり、演出による瞬間的な光 (後述のバースト等) は守備範囲外。

# 3. 心臓部 — 物理法則を使った状態管理 (状態機械)

## 3-1. 基本思想: 「静止した瞬間しか信じない」

盤面は常に動いている: ぷよが落ちる、連鎖が光る、おじゃまが降る。動いている間の読み取りは誤りの温床なので、盤面の状態を常に追跡し (静止 / ツモ落下中 / 連鎖中 / おじゃま落下中 / 重力整地中)、**完全に静止した状態だけを「確定」する**。連鎖中などは直前の確定盤面を凍結して使い続け、ネットの出力は信じない (アクション中は全て物理推論、が鉄則)。

物理ルールに反する読み取りは捨てる: ぷよは浮かない、消えたら上が落ちる、おじゃまは6列に均等に降る (床関数+端数ランダム)、など。

## 3-2. 確定盤面への「書き込み」は2つのドアから入る (重要な構造)

これは今回のバースト調査で決定的に重要になった構造なので詳述する:

**ドア1: 遷移の一括反映** — 「ツモ落下中→静止」「おじゃま落下中→静止」の切り替わりの瞬間、新しく置かれた分の差分を確定盤面に一括で書き込む。設置の反映はここを通る (基準: 設置から8コマ以内に反映)

**ドア2: 静止中のじわじわ修正 (復旧)** — 静止が続いている間、確定盤面と現在の読み取りが食い違うマスを、数コマ連続で同じ値が観測された場合に限り修正する。一時的なノイズはここで弾かれる

この2つのドアは意図的に分離されており、「演出対策のゲート」はドア2だけを守る設計だった — が、**汚染の正門は実はドア1だった**というのが昨夜の大発見 (詳細は§5)。

## 3-3. 隠し段の推論

最上段 (隠し段) は画面にほぼ映らないため、直接は読めない。見えている段のパターンから推論で埋める (隠し段推論)。窒息判定 (3列目の12段目が埋まったら負け。隠し段=13段目に載るだけなら猶予あり) に関わるため重要だが、可視段の情報に依存するので、可視段の扱いを変えると間接的に揺れる (これも昨夜、副作用として実測された)。

# 4. 補助の読み取り器たち

| 読み取り器 | 役割 | 信頼性の現状 |
|---|---|---|
| スコア数字読み取り | 得点の変化から連鎖・攻撃を検出 | 人手検証で誤読ゼロ確認済み (ただし完全破綻する動画が3本あり、それらは除外運用) |
| ネクスト読み取り | 次のぷよ2組 | 48回中48回正解 |
| おじゃま会計 | 「送った・相殺した・降った」の帳簿 | スコア差分方式が最優先、予告表示は補助 |
| 連鎖イベント検出 | 「誰がいつ何連鎖撃ったか」 | **既知の穴あり**: 大連鎖の丸ごと見逃し (お邪魔131個級を0検出した実例)、終局連鎖の18.9%欠落。時間窓の材料としては信頼不可と昨夜確定 |
| 勝敗パネル | 勝ち数の差分で勝者確定 | 承認済み方式 |
| 全消しテロップ | 全消し状態の追跡 | 次のぷよ消去まで残る仕様を反映 |
| 試合境界検出 | 試合の開始・終了 | 境界での内部状態リセット漏れは過去に根治済み |

# 5. 最大の敵 — 画面演出との戦い (現在進行中の最前線)

## 5-1. 敵の姿

ぷよぷよの画面は演出が豊富で、これが読み取りの最大の敵:

- **バースト (お邪魔送付の光)**: 相手が連鎖するたび、自分の盤面上に半透明の光のレイヤーが重なる (ユーザー知見: 5色の半透明レイヤー)。この光でマスの色が化けて読み取られる — **満杯盤面帯の誤り93マスの全ての真因** (人手レビューで確定)
- **煙 (着弾演出)**: おじゃまが自分の盤面に降る瞬間の煙・衝撃。全段に及ぶ
- **連鎖数テロップ・全消しテロップ**: 自分の連鎖中に盤面へ重なる文字
- **白い光沢ハイライト**: ぷよ自体のテカリが「空」と誤読される既知パターン

厄介な物理的事実: **自分へのおじゃま着弾 (=ドア1が開く瞬間) と相手のバースト表示は構造的に同時に起きる** (おじゃまは相手の連鎖完了後に降るため)。つまり誤読が最も起きやすい瞬間と、書き込みの門が開く瞬間が重なっている。

## 5-2. 守りの進化 (3世代の攻防)

**第1世代 (時間ゲート)**: 「相手が連鎖中は上段の修正を保留」。→ 不発。連鎖イベント検出が大連鎖を見逃す・保留規則が長い光で逆転する (0.4秒続いた値を「安定」と誤認) の2つの穴

**第2世代 (案B: 4条件ゲート)**: 時間窓に「自分は連鎖中でない・全消し中でない・実際に光っている」を追加。→ **93マスに対し改善ゼロで見送り**。窓は開いても、汚染はドア2でなくドア1から入っていた

**第3世代 (バーストガード、昨夜実装)**: 3つの構造改革
1. **窓のトリガーを目視 (明るさ検出) に変更** — 信頼できない連鎖イベント検出への依存を廃止。開閉にヒステリシス (一度開いたら最低0.2秒、閉じるには0.25秒の静穏が必要、30秒の安全弁)
2. **保留の論理を反転** — 「0.4秒続いたら採用」をやめ、「光が完全に消えて静穏になってからゼロから数え直し」。光がどれだけ長くても誤確定は原理的に不可能
3. **ドア1に物理フィルタ** (最重要) — 窓が開いている間の遷移一括反映は、「その遷移で物理的にあり得る変化」だけを通す。ツモ設置なら「空→色」だけ、おじゃま落下なら「空→おじゃま」だけ。**「おじゃま落下で既存のぷよが変色する」「9以外の値が湧く」は物理的にあり得ない = バースト誤読の署名**として棄却

正当な設置が遅れない工夫: ドア1のフィルタは「あり得る変化」を素通しするので、光の間の設置も即座に反映される (実測: 通常設置の遅延は完全に無変化)。

## 5-3. 現在の戦況 (2026-08-05朝時点)

- 既知の誤読93マス → **残存33マス (−64.5%)** (30/31本の中間値)
- 通常の設置反映: 無傷。窓中の設置も9割は+2コマ以内
- 残る課題: ①隠し段推論が凍結の影響で揺れる副作用 (対策方向は特定済み) ②光の弱い帯 (明るさ78〜90%) はまだ検出できない (追加較正のラベルが必要) ③長いバースト中の反映遅延テール (最大4.7秒)

# 6. 精度をどう測っているか (測定の文化)

## 6-1. 物差しは人手ラベル

「認識機どうしの答え合わせ」は同じ誤りに合意すると検出できない (自己無矛盾の罠) ため、**正解は必ず人手ラベル**: 実画面を見て1マスずつ正解を付けた盤面ラベル (約3,700マス+満杯盤面帯93マス系) を金の基準にする。

## 6-2. 決定論とbit一致

認識は同じ入力に対して毎回同じ答えを出す (決定論、bit単位の一致で実証済み)。これを利用して、設定が同じなら「アンカー盤面とbit単位で一致する行」を探す方式で厳密な前後比較をする。逆に言うと、**測定と本番で設定が1つでも違うと突合が壊れる** — これで過去に何度も事故った (--with-next抜け、時刻丸めの衝突、など全て記録・根治済み)。

## 6-3. 測定器を疑う文化

昨夜も含め、このプロジェクトの進歩の半分は「測定器のバグ発見」でできている。直近の実例: 誤読自身を「おじゃま増加」と数える循環測定 (98.8%という誤った結論を出しかけて撤回) / 改善が効いた盤面ほど集計から抜ける突合方式の盲点 (効果を過小報告) / 過去の偶然の盤面再現を誤対応させて負の遅延を出すバグ (検収で未然検出)。**数字が出たらまず測定器を検収する**のが標準手順。

## 6-4. 現在の精度の全体像

- 通常帯の持続誤り: 人手検証3,744マスで**ゼロ**
- 遷移瞬間の一時誤り: 1秒以内に自己回復 (学習には時間フィルタで除外、表示には約1秒の遅れとして現れる)
- 満杯盤面帯: 誤り率2.56% → バーストガードで残存1/3まで来た (最終判定はレビュー後)
- 目標: 99.99% (持続誤りベース)。バースト対策完了後に再測定して合否判定

# 7. 速度 — リアルタイムへの道

処理速度は当初の秒4.4コマから**秒31コマへ7倍化**済み (30コマ/秒の実時間を超えた = リアルタイム処理の目処)。効いた施策は「呼び出し1回あたりの無駄を削る」系で、意外な教訓も多い:

- UIマスク判定のマス限定、色分類のまとめ計算などの地道な削減が主力
- **バッチ化は3連続で不発** (まとめて処理すれば速いという直感が外れ続けた)
- **GPUは不採用** (画像をGPUに送る転送コストが計算の節約を食い潰す)
- 速度計測は反復必須・ワンショット禁止 (ばらつきで嘘をつく)
