## 7. 最後に起きたこと: ピンの連鎖と、その正しい直し方

Codex が7本の SHA ガードを依存値契約へ移行した結果、
`scripts/train_advantage_m1_fixed_m0_anchor_v1.py` の SHA が変わり、
**別の4箇所のピンが壊れた** (`MODEL_PROCESS_REGISTRY.json` / `loader.py` の `CODE` /
`g3_source_models.py` の `LOADER_SHA` / テストの `REGISTRY_SHA`)。

最初はレジストリ側を打ち直したが (4箇所、検算72/72)、
**追いかけると4段の連鎖になる**と判明したため止めて調べ直した。

**決め手**: Codex の `guards.patch` を**逆に当てたら元の SHA に完全一致した**
(`855b15f90263...`)。変更は「ガードの前処理」2点だけで**学習の計算は不変**。
そして旧SHA は過去の学習実行の証跡 (`PLAN.json` / `results.json` /
`EXECUTION_PROFILE.json` ほか多数) に埋め込まれている。

> **記録の側を実態に合わせて書き換えるのは方向が逆。ファイル側を戻すのが筋。**

user 承認のもと復元した (B')。結果:

| テスト | 前 | 後 |
|---|---|---|
| `test_g3_model_process.py` | 6 failed | **6 passed** |
| `test_g3_source_models.py` | 4 failed | **11 passed** |
| `test_train_advantage_m1_fixed_m0_anchor_v1.py` | — | **41 passed** (戻しても Codex の修復は壊れていない) |

**ピンは1つも動かさずに済んだ。** 控えは `logs/registry_repin_2026-09-20/` に全部ある。

### G4 への教訓

**同じ「ピンの連鎖」が3回起きた** (Formal100 の二段ピン / 旧SHA直書き7本 / 今回の4段)。
いずれも**変わり続けるファイル全体をピンしている**のが原因。

- `src/production_config.py` は**フラグ台帳**なので採用のたびに必ず変わる。
  これを丸ごとピンする設計は、**採用のたびに壊れる**。
- Formal100 manifest が実際に依存する定数は `GHOST_CHAIN_RULE_ENABLED` **1つだけ**だった。
  ファイル全体でなく**依存している値**を見れば足りる。
- **Codex はこの方向 (依存値契約) へ動き始めている。G4 で完成させること。**
- ただし**学習コードの provenance ピンは別**。あれは「どのコードがこのモデルを作ったか」の
  記録なので、**緩めてはいけない**。今回はコード側を戻すのが正解だった。

  `src/production_config.py` へ採用日と根拠を記録する
