`logs/live_b16/reference_interrupted_b17/` に退避し、状態を推測して継ぎ足さず
offline referenceだけを先頭から再実行して完走した。参照の捨ては0。

## 修正と再現

物理更新を通知ごとの `advance` 要求で子へ渡し、公開時まで貯めない。
通常の更新応答は完了通知のみとし、表示用状態の転送は公開計算時に限定する。
更新と計算は同じ例外隔離経路を通り、HOLD・3連続失敗時の再起動・試合journalからの
再構築を維持する。公開前に試合をまたいだ退避記録も終了時に保存する。

保存入力の最初の5分を同じ508公開時刻で再生すると、勝率・由来の差は0/508。
保存D特徴を再用する再生で、評価計算P95はまとめ更新158.96ms→逐次更新32.04ms。
この再生値には認識・取得待ちを含めない。再現用コマンドは
`python -m scripts.diagnose_live_b17_replay --mode batched` と `--mode fixed`。

実走比較は `python -m scripts.measure_live_b17` でB16末尾と同じ
5880.566〜6180.566秒を各条件5分ずつ直列実行する。
CPU 1スレッド、評価nice 10、event priority ON、公開周期0.5秒は共通。
各条件の前に低負荷60秒を待ち、比較中だけ自分のoffline referenceを停止する。
条件別のSSE・段別時刻・CPU負荷・母数は `logs/live_b17/live/` に保存する。

5分実走の結果（同じ資産・認識設定、両条件とも評価エラー・再起動0）:

- 取得→SSE P95: 306.99ms / 489件 → 217.35ms / 512件（89.64ms、29.2%改善）。
- 認識→評価P95: 239.35→134.66ms。公開計算P95: 235.54→126.10ms。
- 認識処理P95: 32.03→31.94ms。取得待ちP95: 38.67→44.42ms。
  改善は認識の高速化ではなく、評価側の待ちを削った結果である。
- 捨て: 38/8,999（0.422%）→34/8,999（0.378%）。
- 修正前の汚染は0。修正後の2.00秒/60フレームを除外しても
  P95 217.61ms / 509件、捨て33/8,939（0.369%）で結論は変わらない。
- 元の1時間末尾P95 334.43msに対して、新規プロセスの同区間でも306.99msを再現。
  1時間の履歴蓄積を必要としない高遅延で、主因は公開時のまとめ更新である。
  長時間側の追加差は取得待ちにも現れるが、履歴肥大や背景CPU負荷を主因とする
  証拠は得られていない。Windows側の競合・温度・周波数は元記録にないため、
  経時差の上流要因は断定しない。

実走の統合結果は `logs/live_b17/live/report.json`。B14/B16/短区間の段別比較は
`logs/live_b17/saved_diagnosis.json` に保存する。
